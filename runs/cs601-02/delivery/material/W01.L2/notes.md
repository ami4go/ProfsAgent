## 3. Overview of the Model Context Protocol (MCP)

- MCP standardizes how AI models connect to external developer tools and data sources.
- Decouples AI hosts from tool implementations using a client-server architectural pattern.
- Eliminates custom integration glue code for every distinct tool and LLM provider.
- Ensures uniform context retrieval across different IDEs and development environments.

**Notes** (5 min · outcomes CO1.LO1): Model Context Protocol, or MCP, addresses a key bottleneck in AI-assisted development. Traditionally, connecting an LLM agent to local project files, database schemas, or terminal commands required building custom integrations for each specific tool and model. MCP provides an open standard for context exchange. In this architecture, host applications like IDEs act as clients that connect to specialized MCP servers running locally or remotely, providing structured access to context and capabilities.

## 4. MCP Architectural Roles: Host, Client, and Server

- Host application (e.g., IDE or coding agent) initiates AI interactions and user sessions.
- MCP Client maintains connections and negotiates protocol capabilities with servers.
- MCP Server exposes specific resources, tools, and prompts via standardized endpoints.
- Communication follows a strict client-server model over defined transport channels.

AI Host Agent → MCP Client → Transport Layer (stdio/SSE) → MCP Server → Local Workspace Tools

*MCP Communication Flow*

**Notes** (6 min · outcomes CO1.LO1): Understanding the distinction between host, client, and server is essential when reading workspace configurations. The host is the overall application, such as your IDE. The MCP client lives inside or alongside the host to manage connections. MCP servers are independent processes that encapsulate specific developer tools—such as a file system reader, a git helper, or a compiler wrapper. The client and server exchange messages over standard channels like stdio or Server-Sent Events.

## 5. MCP Workspace Configuration Schema

- Workspace configuration defines installed MCP servers under a top-level mcpServers object.
- Each server entry specifies execution command, arguments, and optional environment variables.
- Transport protocol selection defaults to standard input/output (stdio) for local servers.
- Schema strictness requires precise key naming to prevent client initialization failures.

```json
{
  "mcpServers": {
    "workspace-tools": {
      "command": "node",
      "args": ["./mcp-server/index.js"],
      "env": {
        "LOG_LEVEL": "info"
      }
    }
  }
}
```

*Sample MCP Configuration JSON Schema*

**Notes** (6 min · outcomes CO1.LO1): Developer workspace templates configure MCP through a JSON configuration file. The root object contains an mcpServers key, mapping unique server identifiers to their launch definitions. The command field specifies the executable, while args contains array arguments for running the server process. env allows setting environment variables required by the server. If keys are misspelled or arguments are malformed, the client cannot spawn the server process.

## 6. Protocol Handshake and Initialization Requirements

- MCP messaging uses standard JSON-RPC 2.0 specification format.
- Initialization phase begins with an initialize request from client to server.
- Server responds with protocol version, server info, and supported capability flags.
- Client sends initialized notification before executing operational tools or resource queries.

**Notes** (6 min · outcomes CO1.LO1): Underneath the hood, MCP uses JSON-RPC 2.0 for all communications. When an MCP client starts an MCP server process, it must perform a protocol handshake before executing any commands. The client sends an initialize request containing its client version and desired capabilities. The server returns its metadata and capabilities, such as whether it supports resources or tools. Once initialized, the client sends an initialized notification signal, transitioning the connection to active state.

## 7. Categorizing MCP Capabilities: Resources, Tools, Prompts

- Resources supply read-only context data, such as source code files or logs.
- Tools expose executable functions that perform side-effect actions in the workspace.
- Prompts provide pre-configured template structures for recurring developer workflows.
- Configurations must enable capability flags corresponding to required server features.

| Primitive | Primary Purpose | Execution Type | Example Use Case |
|---|---|---|---|
| Resources | Provide passive context | Read-only data retrieval | Reading file content or schema |
| Tools | Perform actions | Executable side-effects | Running tests, committing code |
| Prompts | Guide user interaction | Template expansion | Structuring code review requests |

*MCP Primitive Comparison*

**Notes** (6 min · outcomes CO1.LO1): MCP categorizes interaction capabilities into three core primitives: Resources, Tools, and Prompts. Resources act like read-only GET endpoints in web APIs, allowing the AI to read workspace state safely without side effects. Tools represent callable functions that can modify the workspace—such as compiling code or running unit tests. Prompts are reusable context templates. Identifying which primitive a configuration exports is vital when auditing workspace setups for workflow integration.

## 8. Transport Layers and Execution Isolation

- Stdio transport launches servers as child processes communicating over standard streams.
- Server-Sent Events (SSE) transport enables remote server communication over HTTP.
- Local stdio isolates execution within user permissions and environment boundaries.
- Workspace configuration must explicitly state transport endpoints and authorization headers when using SSE.

**Notes** (6 min · outcomes CO1.LO1): MCP supports two main transport layers: stdio and SSE. In a standard local development setup, stdio is used: the IDE spawns the server binary directly as a subprocess and communicates via standard input and output streams. For remote microservices or team-shared tools, SSE over HTTP is used instead. When auditing a workspace configuration template, you must check whether local binary paths or remote HTTP URLs are specified, ensuring required environment tokens are configured securely.

**In a developer workspace template, which JSON structure correctly defines a local stdio MCP server named 'git-helper'?**

A. {"mcpServers": {"git-helper": {"command": "npx", "args": ["-y", "@mcp/git"]}}}
B. {"tools": [{"name": "git-helper", "exec": "npx -y @mcp/git"}]}

*Answer: A. {"mcpServers": {"git-helper": {"command": "npx", "args": ["-y", "@mcp/git"]}}}. Option 0 correctly uses the top-level mcpServers object with a named server dictionary containing command and args array. Option 1 incorrectly uses a tools array; Option 2 uses an invalid mcp-client format; Option 3 uses non-standard schema keys (path and params instead of command and args).*

## 11. Identifying and Debugging Configuration Schema Issues

- Syntax errors: Missing quotes, trailing commas, or invalid JSON format.
- Schema mismatch: Incorrect top-level key (e.g., servers instead of mcpServers).
- Path issues: Relative executable paths failing when run from different working directories.
- Environment missing: Omitted authorization tokens or missing required environment variables.

**Notes** (7 min · outcomes CO1.LO1): When setting up developer workspace templates, debugging MCP connection failures usually traces back to configuration issues. Common errors include JSON syntax flaws, using non-standard key names like 'servers' or 'plugins' instead of 'mcpServers', or supplying relative binary paths that cannot be resolved by the host process. Always validate the workspace JSON file against the MCP schema specification before running your development agent.
