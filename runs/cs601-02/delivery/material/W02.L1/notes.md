## 3. Introduction to Model Context Protocols

- Model Context Protocol (MCP) standardizes how AI models access external systems and context.
- Eliminates custom one-off integration glue code for every developer tool and repository.
- Enables seamless discovery of local tools, file systems, and external service APIs.

## 4. Why Standardization of Context Matters

- Non-standardized context leads to fragmented tool APIs and fragile prompt engineering.
- Standardized schemas ensure consistent tool signatures and reliable response handling.
- Uniform protocols decouple the AI client from underlying language runtimes and environments.

| Aspect | Custom Integrations | MCP Architecture |
|---|---|---|
| Tool Schema | Ad-hoc JSON or string prompts | Standard JSON Schema specifications |
| Transport | Varies per plugin system | Standard JSON-RPC over stdio or HTTP |
| Scalability | High maintenance overhead | Reusable servers across multiple IDEs |

*Custom Integration vs Standardized MCP Architecture*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Before standardized protocols, connecting an LLM to local file systems or developer tools required custom extensions for each editor or framework. MCP provides a universal interface. Like Language Server Protocol revolutionized code editors, MCP standardizes how AI models read resources, invoke tools, and retrieve context prompts across diverse developer environments.

## 5. High-Level Architecture of Model Context Protocol

- Follows a clean client-server architecture inside the developer workspace.
- Hosts encapsulate the AI application such as an IDE or CLI tool.
- Clients maintain isolated connections with MCP servers handling specific domains.

Host / AI Application → MCP Client → Transport Layer (stdio/HTTP) → MCP Server → External Resource / Tool

*MCP Architecture Data Flow*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): The architecture separates concerns into Host, Client, Server, and Resources. The Host is the top-level application, such as VS Code or an AI CLI. The Client lives inside the Host and manages communication. The MCP Server exposes specific capabilities—like reading git history or running unit tests—via standardized protocol messages.

## 6. MCP Host, Client, and Server Roles

- MCP Host controls application UI, user permissions, and AI orchestration.
- MCP Client initiates protocol handshakes and routes requests to designated servers.
- MCP Server implements capabilities like resources, prompts, and executable tools.

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Understanding these roles is crucial for workspace configuration. The MCP Host acts as the container. It spawns MCP Clients, which establish connections to individual MCP Servers. Each server operates independently in its own process, exposing resources or executable functions while adhering to strict context protocol rules.

## 7. Communication Transports: Stdio vs WebSockets and HTTP

- Stdio transport launches local server subprocesses via standard input and output channels.
- HTTP with Server-Sent Events connects remote or containerized MCP servers.
- Both transports serialize protocol messages using standard JSON-RPC 2.0 format.

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): MCP supports two primary transport mechanisms. Local workspace setups typically use stdio, where the client spawns the server binary directly as a subprocess and communicates over standard input and output. For remote or cloud-hosted tools, HTTP with Server-Sent Events or WebSockets is used. Regardless of transport, the payload structure remains identical JSON-RPC 2.0.

## 8. Core MCP Schema: Server Capabilities

- Servers declare supported features during initial handshake capability negotiation.
- Main capability primitives include resources, prompts, and tools.
- Capability declarations prevent clients from sending unsupported requests to servers.

```json
{
  "protocolVersion": "2024-11-05",
  "capabilities": {
    "resources": {"subscribe": true},
    "tools": {},
    "prompts": {}
  },
  "serverInfo": {
    "name": "workspace-tools",
    "version": "1.0.0"
  }
}
```

*MCP Handshake Server Capabilities Declaration*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): During the initialize exchange, the server sends its capability manifest. This JSON payload lists what the server can handle: whether it provides static context resources, pre-configured prompts, or dynamic executable tools. If a capability is absent, the client knows not to query that feature.

## 9. MCP Schema: Defining Resources

- Resources expose contextual data like files, database schemas, or logs to the AI.
- Expressed using URI templates such as file system paths or custom schemes.
- Resources can be static files or dynamic streams updated via subscription events.

```json

  "name": "Application Entry Point",
```

*MCP Resource Object Definition*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Resources are passive data items that the LLM can attach to its context window. Each resource is identified by a unique URI. When an AI agent needs context about a project, it requests resource contents via the server's resource endpoints.

## 10. MCP Schema: Defining Tools and Arguments

- Tools represent executable functions that perform side effects or computations.
- Schema requires exact tool names, descriptions, and JSON Schema input parameters.
- Client validates LLM arguments against JSON Schema before invoking the server tool.

```json
{
  "name": "run_unit_tests",
  "description": "Executes JUnit test suite",
  "inputSchema": {
    "type": "object",
    "properties": {
      "testClass": {"type": "string"}
    },
    "required": ["testClass"]
  }
}
```

*MCP Tool Specification Schema*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Tools allow the AI model to interact dynamically with the developer workspace—for example, running test suites or formatting code. Tool definitions must strictly follow JSON Schema standards for input parameters so the client can validate the model's output before executing standard functions.

## 11. MCP Schema: Defining Prompts and Context Templates

- Prompts are predefined template messages designed for recurring developer workflows.
- Accept typed parameters to dynamically populate workspace context into prompts.
- Helps standardize prompt engineering patterns across an entire development team.

```json
{
  "name": "code_review",
  "description": "Review pull request diff for bugs",
  "arguments": [
    {
      "name": "targetBranch",
      "description": "Branch to compare against",
      "required": true
    }
  ]
}
```

*MCP Prompt Definition Schema*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Prompts in MCP are reusable workflow templates. Instead of copy-pasting complex system prompts, developers configure prompt templates on the MCP server. The host UI can then surface these prompts with parameterized dropdowns or text inputs.

## 14. Protocol Requirements: JSON-RPC 2.0 Message Structure

- All communications adhere strictly to the JSON-RPC 2.0 specification.
- Request messages include jsonrpc, id, method, and optional params.
- Response messages return matching id, and either result or an error object.

```json
// Request
{
  "jsonrpc": "2.0",
  "id": 101,
  "method": "tools/call",
  "params": {
    "name": "run_unit_tests",
    "arguments": {"testClass": "AppTest"}
  }
}
// Response
{
  "jsonrpc": "2.0",
  "id": 101,
  "result": {
    "content": [{"type": "text", "text": "Tests passed: 5/5"}]
  }
}
```

*JSON-RPC 2.0 Request and Response Pair*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Under the hood, MCP messages travel as line-delimited JSON-RPC 2.0 payloads. Each request carries a unique ID, which the server echoes back in its response. This asynchronous request-response pairing guarantees order tracking across stdio and HTTP streams.

## 15. Parsing Requests and Responses in JSON-RPC (Example)

- Demonstrates handling JSON-RPC requests for resource retrieval.
- Server verifies URI path validity and returns structured resource content.
- Explicit path resolution avoids broken or missing template path strings.

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "resources/read",
  "params": {
    "uri": "file:///workspace/config.json"
  }
}
{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "contents": [
      {
        "uri": "file:///workspace/config.json",
        "mimeType": "application/json",
        "text": "{\"env\": \"production\"}"
      }
    ]
  }
}
```

*Resource Read JSON-RPC Exchange*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Notice how this slide explicitly specifies literal URI paths like file:///workspace/config.json without any unfilled template variables. The request asks to read a specific resource, and the server returns a result array with text content and MIME type.

## 16. Managing Security, Permissions, and Access Control

- MCP tools execute arbitrary code; hosts must enforce strict access boundaries.
- Workspace configurations must restrict server access to explicitly defined roots.
- User confirmation prompts are required before non-read-only tool execution.

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): Security is a core architectural requirement. Because MCP servers can run subprocesses or modify local files, the client and host must enforce security boundaries. Workspace configs should limit directory paths accessible to server binaries, and the host UI must require user consent before executing side-effecting tools.

## 17. Common Configuration Warnings and Protocol Mismatches

- Protocol version mismatch during initialization handshake causes connection rejection.
- Schema validation errors trigger warnings if tool argument types do not match.
- Misconfigured command paths lead to immediate stdio process exit errors.

| Symptom / Warning | Root Cause | Resolution Step |
|---|---|---|
| Unknown protocol version | Client and Server MCP versions differ | Update server package or client version |
| Invalid params schema | Tool arguments violate JSON Schema | Fix schema types in tool definition |
| Process exited with code 1 | Command binary or path not found | Verify executable command and environment args |

*Debugging Common Workspace Configuration Errors*

**Notes** (7 min · outcomes CO1.LO1 · sources [C1]): When setting up a workspace template, you will frequently encounter configuration warnings. Common issues include unsupported protocol versions during the handshake, invalid JSON Schema in tool definitions, or incorrect executable paths in the configuration JSON.
