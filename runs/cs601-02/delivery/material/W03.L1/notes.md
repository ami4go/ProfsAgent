## 5. Recap: Model Context Protocol Core Primitives

- MCP standardizes communication between agent clients and tool or context servers.
- Resources provide readable data sources like source files, logs, and schemas.
- Prompts offer predefined prompt templates for standardized workspace interactions.
- Tools empower agents to run executable functions with specific input parameters.

| Primitive | Purpose | Execution Type |
|---|---|---|
| Resources | Provide contextual read access | Passive data read |
| Prompts | Provide prompt templates | User/Agent parameterization |
| Tools | Perform workspace actions | Active function invocation |

*MCP Core Primitives*

**Notes** (5 min · outcomes CO1.LO2 · sources [C1]): The Model Context Protocol (MCP) establishes a standardized architecture for connecting language models to external tools and data sources. The three fundamental primitives defined by MCP are Resources, Prompts, and Tools. Resources allow the agent to read static or dynamic data such as repository files. Prompts provide structured templates. Tools define executable endpoints that produce side effects, such as running a test suite or invoking a static analyzer.

## 6. Architecting Custom Tool Integrations

- Tool integration exposes local dev utilities like linters and test runners to agents.
- Agents invoke tools via JSON-RPC messages adhering to defined schema contracts.
- Input schemas strictly define valid argument types to guarantee execution safety.
- Server responses return formatted text or content blocks back to the agent context.

Agent generates tool call → MCP Host validates JSON-RPC → Tool Server executes command → Result returned to context

*Tool Execution Pipeline*

**Notes** (5 min · outcomes CO1.LO2 · sources [C1]): When an agent needs to execute an external command, such as invoking a linter or running unit tests, it generates a structured tool call. The host application intercepts this request, validates the arguments against the tool's JSON Schema definition, and forwards it to the tool server. The tool server executes the underlying script and returns JSON-formatted text back to the agent context. This pipeline keeps execution decoupled and safe.

## 9. Example: Defining a Standard MCP Linter Tool (Example)

- MCP tools require `name`, `description`, and `inputSchema` properties.
- JSON Schema inside `inputSchema` specifies argument names, types, and required fields.
- Custom non-standard fields must be omitted to avoid schema validation errors.
- Clean tool definitions ensure static analyzers report zero integration warnings.

```json
{
  "name": "run_linter",
  "description": "Runs static analysis on a target source file",
  "inputSchema": {
    "type": "object",
    "properties": {
      "filePath": {
        "type": "string",
        "description": "Path to source file"
      }
    },
    "required": ["filePath"]
  }
}
```

*Valid MCP Tool Definition*

**Notes** (6 min · outcomes CO1.LO2 · sources [C1]): Here is a standard MCP tool specification for a custom linter tool. Notice that the top-level object contains exactly the standardized MCP fields: name, description, and inputSchema. It does not include non-standard keys like outputSchema or analysisHook which cause schema validation warnings. Sticking to standard MCP definitions ensures smooth tool discovery and error-free configuration in your development environment.
