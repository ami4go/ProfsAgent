## 4. What is the Model Context Protocol (MCP)?

- MCP is an open standard enabling AI models to interact securely with local and remote context sources.
- Decouples AI application hosts from specific tool implementations using standard client-server interfaces.
- Replaces bespoke plug-in adapters with uniform protocol interfaces across development environments.
- Provides structured workflows for context retrieval, template prompts, and executable tool calls.

LLM Host → MCP Client → Protocol Transport → MCP Server → Workspace Tool

*MCP architecture decoupling host applications from workspace tools*

**Notes** (5 min · outcomes CO1.LO2 · sources [C1]): The Model Context Protocol (MCP) solves the N-by-M integration problem in AI-assisted development. Instead of every AI host creating custom drivers for every tool, MCP standardizes how AI applications connect to context providers and tool executors.

## 5. MCP Architecture: Hosts, Clients, and Servers

- An MCP Host (e.g., IDE or agent runner) manages user interactions and coordinates AI sessions.
- An MCP Client maintains a logical connection to a particular MCP Server.
- A host may instantiate multiple clients to communicate with multiple specialized servers simultaneously.
- Communication uses standard transports: local stdio for subprocesses or Streamable HTTP for remote servers.
- HTTP+SSE remains as a legacy transport mechanism in older implementations.

**Notes** (6 min · outcomes CO1.LO2 · sources [C1]): It is critical to understand the relationship between Hosts, Clients, and Servers. An MCP Host coordinates the application. To connect to tools, the host creates separate MCP Clients. Each MCP Client maintains a logical connection to a single MCP Server. If a workspace uses three servers (a database server, a linter server, and a git server), the host creates three clients. Standard transports include stdio for local child processes and Streamable HTTP for network services, while HTTP+SSE is a legacy transport.

## 6. MCP Core Primitives: Resources, Prompts, and Tools

- Resources expose readable context data like log files, database schemas, or workspace documentation.
- Prompts provide reusable template structures to guide model reasoning for specific tasks.
- Tools allow models to perform side-effect actions such as running builds or invoking static analyzers.
- Tools use JSON Schema to define their input arguments so models know how to call them.
- Tool execution results return as structured MCP content, including text, images, or resource references.

| Primitive | Direction | Purpose | Data Format |
|---|---|---|---|
| Resources | Server to Client | Expose readable context | Text / Binary Data |
| Prompts | Server to Client | Provide contextual templates | Prompt Messages |
| Tools | Client to Server | Execute workspace actions | JSON Input / Content Output |

*Comparison of MCP Core Primitives*

**Notes** (6 min · outcomes CO1.LO2 · sources [C1]): MCP defines three core primitives: Resources, Prompts, and Tools. Notice the distinct role of Tools: they are designed for actions that modify state or execute commands in the workspace. Tools define their accepted input arguments using JSON Schema, while their output is returned as structured MCP content blocks like text stdout, error reports, or images.

## 7. Tool Schema Definitions and Input Validation

- Tools declare exact parameter types, descriptions, and required fields using JSON Schema format.
- Clear parameter descriptions guide model call generation, reducing malformed parameter attempts.
- Schema guidance reduces but does not eliminate malformed tool call attempts by models.
- Server-side validation rejects invalid arguments before executing actual tool or shell logic.
- Structured error responses inform the agent of validation failures so it can retry correctly.

**Notes** (6 min · outcomes CO1.LO2): Defining a clean JSON Schema is necessary for the AI model to construct valid calls. However, never rely on the model alone for system security or program safety. Schema guidance reduces malformed calls, but the MCP Server must validate incoming arguments on the server side before executing any shell command or linter.

## 10. Implementing a Custom MCP Tool Server (Example)

- Server validates incoming arguments against the tool schema prior to executing workspace commands.
- Actual tool invocation occurs safely after parameter verification.
- Return responses formatted as MCP content blocks containing stdout or structured error reports.

```typescript
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { CallToolRequestSchema } from "@modelcontextprotocol/sdk/types.js";
import { execSync } from "child_process";

server.setRequestHandler(CallToolRequestSchema, async (req) => {
  const { name, arguments: args } = req.params;
  if (name !== "run_linter") throw new Error("Unknown tool");
  const path = String(args?.filePath || "");
  const linter = String(args?.linterName || "");
  if (!path || !["eslint", "flake8"].includes(linter)) {
    return { content: [{ type: "text", text: "Error: Invalid tool arguments supplied." }] };
  }
  try {
    const stdout = execSync(`${linter} ${path}`).toString();
    return { content: [{ type: "text", text: stdout || "Linting passed with 0 errors." }] };
  } catch (err: unknown) {
    const msg = err instanceof Error ? err.message : String(err);
    return { content: [{ type: "text", text: `Linter failed: ${msg}` }] };
  }
});
```

*TypeScript server handling run_linter request with parameter validation*

**Notes** (8 min · outcomes CO1.LO2): Here is a complete server handler implementation in TypeScript. Notice two essential practices: first, we explicitly validate that filePath and linterName match our expected constraints before calling execSync. Second, we capture errors safely using modern TypeScript typing.

## 13. Fixing Configuration and Analysis Warnings (Example)

- Common warning: Catch blocks using err.message fail strict compiler checks when err is unknown.
- Fix: Narrow the unknown type safely using an instanceof Error guard before accessing properties.
- Common config warning: Missing server configuration fields or unvalidated input parameter types.
- Ensuring zero static analysis warnings guarantees reliable agent tool invocation during integration tests.

```typescript
function getErrorMessage(err: unknown): string {
  if (err instanceof Error) {
    return err.message;
  }
  if (typeof err === "object" && err !== null && "message" in err) {
    return String((err as { message: unknown }).message);
  }
  return String(err);
}

try {
  const res = execSync("eslint src/index.ts");
} catch (err: unknown) {
  const safeMessage = getErrorMessage(err);
  console.error("Static analysis output:", safeMessage);
}
```

*Type-safe error narrowing function preventing compiler diagnostics*

**Notes** (8 min · outcomes CO1.LO2): Notice how the catch block types `err` as `unknown`. Accessing `err.message` directly causes a static analyzer diagnostic error. By creating a helper with an `instanceof Error` guard, we satisfy strict compiler checks and avoid runtime crashes.
