## 3. Model Context Protocol for Agent Tool Integrations

- Model Context Protocol (MCP) standardizes how AI agents communicate with external development tools and servers.
- Context servers expose tools, resources, and prompt templates through a standardized JSON-RPC schema.
- Standardized interfaces decouple model capabilities from specific workspace implementations.

AI Agent Workspace → MCP Protocol Interface → Tool Server → External API/DB

*MCP Architecture Flow*

## 4. Architecture of MCP Tool Servers

- MCP architecture separates the host client from isolated server tools.
- Tools are registered with strict JSON Schema parameter definitions for model validation.
- Transport options include stdio for local tools and Server-Sent Events (SSE) for remote services.

| MCP Client | Workspace host requesting actions | VS Code Agent Extension |
|---|---|---|
| MCP Server | Exposes executable tools & data | Custom Git/Database Server |
| Tool Definition | JSON schema defining input parameters | run_linter(path, rules) |
| Transport Layer | Communication channel | stdio / HTTP-SSE |

*MCP System Components*

**Notes** (5 min · outcomes CO1.LO2 · sources [C1]): The architecture relies on a client-server structure. The client is typically the workspace IDE or agent runtime. The tool server executes functions locally or remotely. Defining strict JSON schemas for inputs ensures that LLM agent function calls can be validated prior to execution.

## 5. Implementing an MCP Tool Server (Worked problem)

- Define explicit input/output schemas using typed function signatures.
- Implement error handling directly in the tool handler to avoid runtime crashes.
- Return formatted strings or JSON structures that agents can interpret directly.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("code-analysis-server")

@mcp.tool()
def run_static_analysis(file_path: str) -> str:
    """Run static analysis on a file and return report."""
    if not file_path.endswith(".py"):
        return "Error: Only Python files supported"
    # Execute linter and return clean result
    return "0 errors, 0 warnings"

if __name__ == "__main__":
    mcp.run()
```

*Python FastMCP Tool Implementation*

Notice how parameter types and docstrings serve as the specification for the AI agent. The function signature and docstring tell the LLM what inputs are required and what the tool accomplishes.

## 9. Defining Actors and External Interfaces

- Actors must always be external entities (human users or external systems) interacting with the system.
- The software system being designed is NEVER an actor itself.
- Primary actors trigger use cases; secondary actors assist in completing them.

| Primary Actor | User initiating interaction to achieve a goal | Store Customer |
|---|---|---|
| Secondary Actor | External system or role providing services | Payment Gateway |
| System Boundary | Limit dividing internal logic from actors | E-commerce API |
| System Administrator | Actor managing configuration and access | System Administrator |

*Actor Identification Matrix*

**Notes** (6 min · outcomes CO2.LO3): A critical rule in system modeling: actors are external entities that interact with your system. Humans like 'Customer' or external systems like 'Payment Gateway' or operational actors like 'System Administrator' are actors. The system under design is inside the boundary, so it can never be an actor.

## 10. Standard Specification Guidelines for Use Cases

- Standard use case templates ensure consistency across development teams.
- Preconditions state necessary requirements before execution can begin.
- Main success scenarios document step-by-step user interactions and system responses.
- Postconditions define system state changes after successful completion.

Name & Goal → Actors → Preconditions → Main Success Scenario → Postconditions

*Use Case Specification Anatomy*

**Notes** (6 min · outcomes CO2.LO3): Following a standardized specification format keeps requirements unambiguous. Every short use case should capture the goal, external actors, preconditions, step-by-step interaction flow, and postconditions.

## 12. From Product Description to Use Cases (Worked problem)

- Primary actor (System Administrator) initiates the dispatch workflow.
- External partner (Carrier) acts as a secondary actor providing routing data.
- Note: The internal software system coordinates actions but is not listed as an actor.
- Preconditions and postconditions explicitly lock down state transition criteria.

```yaml
use_case: Dispatch Package Delivery
primary_actor: System Administrator
secondary_actor: Carrier
preconditions:
  - Customer order is paid and verified.
main_flow:
  1. System Administrator selects pending package for dispatch.
  2. System requests delivery route from Carrier.
  3. Carrier returns tracking ID and estimated arrival.
  4. System Administrator confirms assignment.
postconditions:
  - Package status set to Dispatched with assigned tracking ID.
```

## 14. Handling Ambiguity in Specifications

- Unstructured requirements often use vague language like 'fast' or 'secure'.
- AI tools require structured, concrete conditions to generate accurate code/tests.
- Transform vague expectations into measurable SLA targets and boundary events.

| 'Fast system responses' | Unmeasurable goal | Specify SLA: latency < 200ms |
|---|---|---|
| 'Process payments safely' | Undefined external actor | Explicitly integrate Payment Gateway |
| 'System updates status' | Missing primary trigger | Carrier sends status update callback |

*Ambiguity Resolution Patterns*

**Notes** (6 min · outcomes CO2.LO3): When converting requirements into executable specs, watch out for vague claims. AI coding assistants fail or hallucinate when specifications contain ambiguous terms. Clarifying boundaries and metrics ensures both human developers and AI agents produce correct code.
