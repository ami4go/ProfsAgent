## 3. From Product Description to Use Cases

- Unstructured product descriptions are the starting point
- Standards give a shared vocabulary
- Spec‑driven development turns descriptions into executable specs

**Notes** (4 min · outcomes CO2.LO3, CO2.LO1): Open the lecture by framing the problem: we receive a narrative product description and must produce precise use cases. Standards provide the common language that lets analysts, developers, and testers agree on what the system must do. Spec‑driven development then uses those use cases as executable specifications that can drive code generation and test creation.

## 4. Why Use‑Case Standards Matter

- Common language for stakeholders
- Enables traceability to code and tests
- Supports tooling and automation

**Notes** (4 min · outcomes CO2.LO3, CO2.LO1): Without a standard notation, each team invents its own way of writing use cases, leading to ambiguity and gaps. A shared standard lets requirements be traced forward to design, code, and test cases, and it enables tools to parse, validate, and even generate artifacts automatically.

## 5. Key Use‑Case Standards: UML 2.x & OMG Template

- UML 2.x defines use‑case diagram notation
- OMG provides a textual use‑case template
- Both are maintained by the Object Management Group

Actor → Use Case → Include/Extend → System Boundary

*Core elements of a UML use‑case diagram*

**Notes** (5 min · outcomes CO2.LO3, CO2.LO1): UML 2.x is the de‑facto graphical standard for use‑case diagrams; the OMG also publishes a textual template (often called the Cockburn template) that captures preconditions, postconditions, main flow, and alternatives. Both are actively maintained and widely supported by modeling tools.

## 6. Requirements Specification Standard: ISO/IEC/IEEE 29148

- Replaces withdrawn IEEE 830 (2017)
- Structures SRS: purpose, scope, functional & non‑functional requirements
- Guides traceability and verification

**Notes** (5 min · outcomes CO2.LO3, CO2.LO1): IEEE 830 was withdrawn in 2017. The current international standard for writing Software Requirements Specifications is ISO/IEC/IEEE 29148, which defines the required sections of an SRS and emphasizes bidirectional traceability between requirements, design, and test.

## 7. Quality Model: ISO/IEC 25010

- Defines product quality characteristics (e.g., functionality, reliability)
- Not a use‑case standard but informs non‑functional requirements
- Used to derive quality‑focused use cases

**Notes** (4 min · outcomes CO2.LO3, CO2.LO1): ISO/IEC 25010 (2018 edition) provides a taxonomy of quality attributes such as performance, security, and usability. While it does not define use‑case notation, it is the reference for writing non‑functional requirements that later become quality‑focused use cases or acceptance criteria.

## 9. Identifying the System Boundary

- Boundary encloses responsibilities of the system under design
- Actors and external systems stay outside
- Clarifies scope for development and testing

**Notes** (4 min · outcomes CO2.LO3, CO2.LO1): The system boundary is a conceptual line that separates what the project team must build from what is given (actors, external services, hardware). It is drawn on the use‑case diagram as a rectangle; everything inside is in scope, everything outside is an actor or an external system.

## 11. Spec‑Driven Development Guidelines for Use Cases

- Write use cases as executable specifications
- Link each use case to acceptance criteria
- Generate test scaffolding from use‑case steps

**Notes** (5 min · outcomes CO2.LO3, CO2.LO1 · sources [C2]): Spec‑driven development treats a well‑structured use case (with clear preconditions, main flow, and postconditions) as a living specification. Tools can parse the steps to generate BDD‑style test skeletons, API contracts, or even prototype code, keeping implementation aligned with requirements.

## 14. Software Requirements Engineering Overview

- Elicitation, analysis, specification, validation, management
- Iterative and incremental in modern practice
- Bridges stakeholder needs and technical solution

**Notes** (4 min): Requirements engineering is the disciplined process of discovering, documenting, and maintaining what the software must do. It is not a one‑shot activity; modern projects revisit each phase as knowledge grows.

## 15. Requirements Elicitation Techniques

- Interviews and workshops
- Observation and ethnography
- Prototyping and storyboarding

| Technique | Strength | Weakness |
|---|---|---|
| Interviews | Deep insight | Time‑consuming |
| Workshops | Consensus building | Groupthink risk |
| Prototyping | Early feedback | Scope creep |

*Common elicitation techniques compared*

**Notes** (4 min): No single technique suffices. Interviews uncover detailed needs, workshops align stakeholders, and prototypes make abstract ideas concrete. Combining them reduces the risk of missing critical requirements.

## 16. Requirements Analysis & Modeling

- Use cases and user stories capture functional needs
- Domain models clarify data concepts
- Non‑functional requirements mapped to ISO/IEC 25010

**Notes** (4 min): Analysis transforms raw elicitation data into structured models. Use cases (or user stories) describe behavior; domain models (class diagrams, ER diagrams) capture data; quality attributes from ISO/IEC 25010 become non‑functional requirements with measurable targets.

## 17. Requirements Specification & Validation

- SRS structured per ISO/IEC/IEEE 29148
- Reviews, inspections, and prototypes validate completeness
- Traceability matrix links requirements to tests

**Notes** (4 min): The SRS is the contract between stakeholders and developers. Following ISO/IEC/IEEE 29148 ensures all required sections exist. Validation uses peer reviews, executable prototypes, and a traceability matrix to confirm every requirement is testable and covered.

## 18. Requirements Management & Traceability

- Version control for requirements artifacts
- Change impact analysis via trace links
- Tool support (e.g., DOORS, Jama, Git‑based)

**Notes** (4 min): Requirements evolve. A management process stores each version, records rationale, and maintains trace links to design, code, and tests. When a requirement changes, impact analysis shows which downstream artifacts must be updated. Modern tools integrate with Git to keep requirements close to the codebase.
