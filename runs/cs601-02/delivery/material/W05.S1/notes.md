## 4. The Requirements Engineering Challenge in AI Coding

- Unstructured product descriptions cause AI model hallucinations and scope creep.
- Generative models require explicit boundaries to avoid generating unrequested assumptions.
- Structured specifications serve as deterministic prompt anchors and validation criteria.

**Notes** (6 min · outcomes CO2.LO1 · sources [C4]): When stakeholders give us product ideas, they usually arrive as loose prose, informal emails, or incomplete user stories. If you feed unstructured text directly into an LLM coding agent, the agent fills in missing gaps with random assumptions. This introduces subtle bugs and architectural drift. Requirements engineering in the AI era is about transforming ambiguous language into unambiguous system constraints that anchor the AI's generation process.

## 5. Fundamentals of Specification-Driven Development

- Specification-Driven Development formalizes specifications before writing source code.
- Specifications serve as the single source of truth for humans and AI agents.
- Reduces downstream debugging by catching architectural ambiguity upfront.

**Notes** (6 min · outcomes CO2.LO1 · sources [C2]): Specification-Driven Development, or SDD, flips the traditional prompt-and-fix workflow. Instead of writing code directly or asking an AI to write code from a short prompt, SDD requires us to construct a rigorous specification document first. This document acts as a formal contract. Both human developers and automated coding agents treat this contract as the immutable specification baseline.

## 6. Deconstructing Unstructured Product Descriptions

**Notes** (7 min · outcomes CO2.LO1): To translate raw product text into specifications, we must systematically deconstruct narrative language. Look for passive phrasing like 'data is processed' and ask who or what processes it. Break down dense paragraphs into explicit actors, trigger events, strict preconditions, and verifiable postconditions. This structured decomposition removes ambiguity before any code generation tools are invoked.

## 9. Formulating Out-of-Scope Constraints

- Explicitly listing out-of-scope items prevents feature creep and agent over-generation.
- Defines system interfaces by specifying what the module will deliberately omit.
- Establishes rigid architectural boundaries for generated software components.

**Notes** (6 min · outcomes CO2.LO1): Engineers often forget to define what a system should NOT do. When working with AI generators, unstated non-goals lead to bloat. If you specify an authentication service, explicitly state that user registration and password resets are out of scope if handled elsewhere. Out-of-scope boundaries keep generated code lean, modular, and strictly aligned with specified tasks.

## 11. Structuring Ambiguous Text into Formal Contracts

- Convert prose into structured schemas like Gherkin, YAML, or JSON-spec.
- Standardized schemas enforce consistent parsing by automated tools and agents.
- Structured contracts support automated specification validation and test generation.

**Notes** (7 min · outcomes CO2.LO1 · sources [C2]): Once we extract use cases and system boundaries, we must format them into structured specifications. Informal text leads to varied interpretations. By standardizing our specs into formats like Gherkin syntax or structured YAML schemas, we create machine-readable contracts. These contracts can be validated for completeness before any code generation takes place.

## 12. Managing Complexity Backpressure in Requirement Specs

- Monolithic requirement documents cause performance decay in AI coding agents.
- Partition specs into modular, hierarchically organized domain specifications.
- Mitigates complexity backpressure across multi-step autonomous software tasks.

**Notes** (7 min · outcomes CO2.LO1 · sources [C3]): Research shows that AI coding performance drops significantly as task complexity and prompt size increase—a phenomenon known as complexity backpressure. If you feed an entire 50-page requirements document to an agent, accuracy plummets. Instead, engineering guidelines dictate decomposing requirements into small, self-contained sub-specifications focused on specific use cases.

## 13. YAML Specification Artifact Walkthrough (Example)

- Examines a structured YAML specification derived from unstructured product descriptions.
- Demonstrates clear allocation of use cases, boundary inputs, and expected outcomes.
- Serves as an input schema for spec-driven code generation frameworks.

```yaml
use_case:
  id: UC-01
  title: Process Invoice Upload
  actor: User
  boundary:
    in_scope: [Format Validation, Error Response]
    out_of_scope: [Payment Execution, Cloud Storage]
  preconditions:
    - User is authenticated
  scenario:
    given: A PDF file uploaded by the user
    when: File size is under 10MB
    then: Validate schema and return status code 200
```

*Structured Specification Example*

**Notes** (8 min · outcomes CO2.LO1 · sources [C2]): Here is an example of a specification artifact written in YAML. Notice how clear and concise this is compared to a raw client paragraph. It explicitly lists the actor, the in-scope responsibilities, the out-of-scope boundaries, and a Gherkin-style test scenario. An AI agent reading this spec receives exact instructions without ambiguity.
