## 4. What Is Spec-Driven Development?

- Specification is the single source of truth
- Code is generated or validated against the spec
- Reduces documentation drift by making the spec authoritative
- Enables contract‑first development across teams

**Notes** (6 min · sources [C1]): Spec‑driven development (SDD) treats the specification as the authoritative artifact. Instead of writing code first and documenting later, the spec defines the contract; implementation is then generated or continuously validated against it. This approach reduces documentation drift because the spec drives both client and server code, and any change must be reflected in the spec before code is updated. The key idea is a closed loop: spec → generate/validate → deploy.

## 5. Core Principles of Spec-Driven Development

- Contract‑first design
- Machine‑readable specifications
- Automated code generation or validation
- Versioned, reviewable spec artifacts

**Notes** (5 min · sources [C1]): The four pillars of SDD are: (1) design the contract before any implementation, (2) express the contract in a machine‑readable format (OpenAPI, GraphQL SDL, Protobuf), (3) use tooling to generate stubs, clients, or run conformance tests, and (4) store the spec in version control so it can be reviewed like code. These principles ensure that every public method matches the agreed interface.

## 6. Major Spec-Driven Frameworks

- OpenAPI (REST/HTTP)
- GraphQL Schema Definition Language
- Protocol Buffers (gRPC)

**Notes** (5 min · sources [C1]): Three dominant frameworks cover the main API styles: OpenAPI for RESTful HTTP services, GraphQL SDL for flexible query‑based APIs, and Protocol Buffers for high‑performance RPC (often with gRPC). Each provides a language‑agnostic schema, tooling for code generation, and validation libraries. The choice depends on team expertise, performance needs, and ecosystem.

## 7. OpenAPI 3.1 Structure

- info, servers, paths, components
- Reusable schemas in components/schemas
- Security schemes and callbacks
- Extensible with vendor extensions (x‑*)

**Notes** (6 min · sources [C1]): An OpenAPI document starts with metadata (info, servers). The paths object maps HTTP endpoints to operations. Reusable data models live under components/schemas, enabling DRY definitions. Security schemes describe authentication (API keys, OAuth2). Vendor extensions allow tool‑specific metadata without breaking the standard.

## 8. GraphQL Schema Definition Language

- Type system: scalar, object, interface, union, enum
- Root operation types: query, mutation, subscription
- Built‑in directive @deprecated
- Custom directives can carry metadata such as authorization hints or caching policy

**Notes** (6 min · sources [C1]): GraphQL SDL defines a strong type system. The schema must declare root query, mutation, and optional subscription types. The only built‑in directive is @deprecated; however, developers frequently define custom directives (e.g., @auth, @cacheControl) to attach application‑level metadata. These directives are not part of the GraphQL spec but are widely used by tooling.

## 9. Protocol Buffers (proto3) Basics

- Message definitions with field numbers
- Service definitions for RPC
- Scalar types: string, int32, bool, bytes, etc.
- Generated code for multiple languages

**Notes** (6 min · sources [C1]): Protobuf uses a compact binary wire format. A .proto file declares messages (data structures) with numbered fields and services (RPC interfaces). The protoc compiler reads the .proto file and generates client/server stubs in languages such as Go, Java, Python, and TypeScript. Field numbers must remain stable for backward compatibility.

## 10. Worked Example: User Login API – OpenAPI (Worked problem)

- Define request/response schemas
- Mark password as writeOnly
- Add minLength constraints
- Generate server stub from spec

```yaml
openapi: 3.1.0
info:
  title: Auth API
  version: 1.0.0
paths:
  /login:
    post:
      summary: User login
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [username, password]
              properties:
                username:
                  type: string
                  minLength: 3
                password:
                  type: string
                  writeOnly: true
                  minLength: 8
      responses:
        '200':
          description: Successful login
          content:
            application/json:
              schema:
                type: object
                properties:
                  token:
                    type: string
```

*OpenAPI 3.1 snippet for a login endpoint*

**Notes** (8 min · outcomes CO2.LO2 · sources [C1]): Walk through the spec line by line: the info block, the /login path with a POST operation, a requestBody that references a schema requiring username and password. Note the password field uses writeOnly: true and minLength instead of a non‑standard format. The 200 response returns a token. Show how a tool like openapi-generator can produce a server skeleton that enforces this contract.

## 11. Worked Example: User Login API – GraphQL SDL (Worked problem)

- Define Login mutation input and payload
- Use custom @auth directive for metadata
- Return token and user object
- Schema is executable with GraphQL servers

```graphql
type Query {
  login(username: String!, password: String!): AuthPayload
}

type AuthPayload {
  token: String!
  user: User!
}

type User {
  id: ID!
  username: String!
  email: String!
}

# Custom directive for auth metadata
directive @auth(requires: String) on FIELD_DEFINITION
```

*GraphQL SDL for login mutation*

**Notes** (8 min · outcomes CO2.LO2 · sources [C1]): Explain the SDL: a Query type with a login field that takes username and password and returns AuthPayload. AuthPayload contains a token and a User object. The custom @auth directive illustrates how teams attach authorization hints (e.g., required roles) without extending the GraphQL spec. Tools like Apollo Server can read these directives for middleware.

## 12. Worked Example: User Login API – Protobuf (Worked problem)

- Define LoginRequest and LoginResponse messages
- Service AuthService with Login RPC
- Use protoc to generate gRPC stubs
- Field numbers ensure wire compatibility

```protobuf
syntax = "proto3";

package auth;

service AuthService {
  rpc Login(LoginRequest) returns (LoginResponse);
}

message LoginRequest {
  string username = 1;
  string password = 2;
}

message LoginResponse {
  string token = 1;
  User user = 2;
}

message User {
  string id = 1;
  string username = 2;
  string email = 3;
}
```

*Protobuf definition for login service*

**Notes** (8 min · outcomes CO2.LO2 · sources [C1]): Show the .proto file: package declaration, service with a single RPC, request/response messages, and a nested User message. Emphasize that field numbers (1,2,…) are part of the wire format and must not be reused. Running protoc with the gRPC plugin produces client and server interfaces in the target language, guaranteeing that the generated code matches the spec exactly.

## 13. From Requirements to Executable Specs

- Identify use cases and actors
- Map each use case to an API operation
- Choose spec framework per service style
- Write spec, review, version, and baseline

**Notes** (5 min · outcomes CO2.LO2 · sources [C1]): The translation process starts with the requirements document. For each use case, define the external interface (REST endpoint, GraphQL mutation, gRPC method). Select the appropriate spec language. Author the spec collaboratively, run linting (e.g., spectral for OpenAPI), and store it in version control. The spec then becomes the baseline for code generation and contract testing.

## 14. Ensuring Interface Conformance at Runtime

- Contract testing with generated clients
- JSON Schema validation libraries (ajv)
- Protocol Buffers compiler (protoc) for code generation
- CI pipelines enforce spec compliance

**Notes** (6 min · outcomes CO2.LO2 · sources [C1]): Runtime conformance is achieved by (1) generating client SDKs from the spec so callers cannot send invalid payloads, (2) validating incoming requests against JSON Schema using libraries such as ajv, (3) using protoc to compile .proto files into type‑safe stubs that reject mismatched messages, and (4) embedding these checks in CI/CD so any drift fails the build. This closes the loop between spec and implementation.

## 15. Check: Spec-Driven Development Principle (Check)


**Which statement best describes the core principle of spec‑driven development?**

A. Write code first, then generate documentation from the implementation.
B. Treat the specification as the authoritative contract and generate or validate code against it.
C. Use informal comments in code as the primary source of API contracts.
D. Maintain separate documentation and code repositories with manual sync.

*Answer: B. Treat the specification as the authoritative contract and generate or validate code against it.. Option B captures the contract‑first mindset: the spec is the single source of truth and drives code generation or validation. Option A is the traditional code‑first approach, which leads to drift. Option C relies on informal comments, not machine‑readable specs. Option D describes a manual process that spec‑driven development aims to eliminate.*

**Notes** (4 min · outcomes CO2.LO2): This quick poll checks that students grasp the fundamental shift from code‑first to spec‑first. Discuss why the other options are common misconceptions.
