## 6. Example: Requirement → Spec (Example)

- Requirement: "User can withdraw cash if balance sufficient"
- Spec written in Gherkin
- Covers happy path and insufficient‑funds path

```gherkin
Feature: Cash withdrawal
  Scenario: Sufficient balance
    Given the account balance is $100
    When the user requests $60
    Then the dispenser provides $60
    And the account balance becomes $40
  Scenario: Insufficient balance
    Given the account balance is $30
    When the user requests $60
    Then the transaction is rejected
    And the account balance remains $30
```

*Gherkin spec for cash withdrawal*

**Notes** (6 min · outcomes CO2.LO2): Present the two scenarios side‑by‑side. Highlight that each step maps directly to a method contract (e.g., `withdraw(amount) -> Result`). The spec is executable: a test runner can invoke the system under test and verify the post‑conditions automatically.

## 7. Worked Problem: Translate Requirement to Spec & Generate Code (Worked problem)

- Step 1: Extract actors, actions, data
- Step 2: Write Gherkin scenarios
- Step 3: Derive method signatures
- Step 4: Prompt AI model for implementation
- Step 5: Run generated tests against spec

```python
def withdraw(account: Account, amount: Decimal) -> Result:
    if amount <= 0:
        return Result.fail("Amount must be positive")
    if account.balance < amount:
        return Result.fail("Insufficient funds")
    account.balance -= amount
    return Result.ok(account.balance)
```

*Generated Python withdrawal method*

## 10. Iterative Loop Engineering Recap

- Loop: plan → generate → execute → reflect
- Agents produce code, tests, and logs
- Each iteration refines the artifact

**Notes** (5 min · outcomes CO3.LO1): Briefly recap the iterative loop engineering cycle introduced in the previous week. Emphasize that the loop is driven by execution logs, which capture every control‑flow decision made by the coding agent. This sets the stage for trace analysis (CO3.LO1).

## 11. Loop Engineering Phases

- Plan: define goal and constraints
- Generate: agent writes code/tests
- Execute: run in sandbox, collect logs
- Reflect: analyse logs, decide next step

Plan → Generate → Execute → Reflect

*Four phases of an engineering loop*

**Notes** (6 min · outcomes CO3.LO1): Detail each phase. In Plan, the human or a planner agent states the objective (e.g., implement `withdraw`). Generate invokes the coding agent. Execute runs the code in an isolated environment, producing a structured log. Reflect parses the log to detect errors, performance issues, or spec violations, then feeds insights back to Plan.

## 15. Check: Loop Engineering & Tracing (Check)


**In an iterative loop engineering log, which event type most directly reveals a branch decision that caused a spec violation?**

A. CALL
B. RETURN
C. BRANCH
D. REFLECT

*Answer: C. BRANCH. BRANCH events record the outcome of conditional statements. A mismatch between the expected branch (per spec) and the logged branch pinpoints the exact control‑flow deviation. CALL/RETURN show entry/exit but not the decision.*

**Notes** (3 min · outcomes CO3.LO1): Reinforce that BRANCH entries are the key to tracing control‑flow errors. The distractor RETURN is tempting because it shows the result, but it does not expose the decision logic.
