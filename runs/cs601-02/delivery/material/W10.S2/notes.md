## 3. Why automated testing matters for AI-generated code

- AI code is nondeterministic and may hide subtle bugs
- Manual review does not scale with generated volume
- Automated pipelines give fast, repeatable confidence
- Testing must cover syntax, semantics, and runtime behavior

**Notes** (5 min · outcomes CO4.LO1 · sources [C4]): AI-native software factories produce large amounts of code from models that can hallucinate or misinterpret specifications. Because the output varies across runs, a single manual inspection cannot guarantee quality. Automated testing provides a systematic, repeatable way to catch regressions, enforce contracts, and measure reliability before deployment. This slide sets the motivation for the entire lecture.

## 4. Testing pyramid adapted for AI-native pipelines

- Unit tests: check individual generated functions
- Integration tests: verify component interactions
- System tests: run end‑to‑end scenarios with real data
- Property‑based tests: express invariants that must hold for all outputs

**Notes** (5 min · outcomes CO4.LO1 · sources [C4] [C6]): The classic testing pyramid still applies, but the layers shift. Unit tests are often generated alongside code; integration tests must exercise the boundaries where AI‑generated modules meet hand‑written ones; system tests use realistic workloads; property‑based tests capture high‑level specifications that are hard to enumerate as concrete cases. This structure guides where to invest automation effort.

## 5. Static analysis and specification‑driven checks

- Specifications written in a formal or semi‑formal language
- A spec checker verifies generated code against the spec
- Catches type errors, contract violations, and missing cases
- Runs before any code execution, cheap and fast

**Notes** (5 min · outcomes CO4.LO1 · sources [C2]): Specification‑driven development (C2) lets developers write pre‑ and post‑conditions, invariants, or interface contracts. A static verifier then proves that the generated implementation satisfies those contracts without executing it. This early gate eliminates a whole class of defects and reduces the load on later dynamic testing stages.

## 6. Specification‑driven example (pseudocode) (Example)

- Spec: sort(input) returns output such that output is a permutation of input and is sorted
- Generated code: function sort(arr) { … }
- Static checker validates: isPermutation(input, output) ∧ isSorted(output)
- Checker runs as a separate tool, not as part of the language runtime

```text
// Specification (in a contract language)
spec sort(input: List<int>) -> output: List<int> {
  requires true;
  ensures isPermutation(input, output) && isSorted(output);
}

// Generated implementation (pseudocode)
function sort(arr) {
  // ... sorting algorithm ...
  return sortedArr;
}

// Static verification step (conceptual)
verify(sort, spec);
```

*Pseudocode illustration of a spec and a static check*

**Notes** (6 min · outcomes CO4.LO1 · sources [C2]): The slide shows a tiny contract for a sorting function. The spec states two post‑conditions: the output must be a permutation of the input and must be sorted. The generated code is not executed; instead a separate verification tool (e.g., an SMT‑based checker) proves that the implementation meets the spec for all possible inputs. This illustrates how static specification checks differ from ordinary type checking.

## 7. Dynamic testing: execution‑based test generation

- Fuzzing generated functions with random inputs
- Property‑based frameworks (e.g., Hypothesis) derive test cases from specs
- Differential testing: compare AI output with a trusted reference
- Collect coverage to guide further generation

**Notes** (5 min · outcomes CO4.LO1 · sources [C1] [C6]): Static checks cannot catch all semantic errors. Dynamic testing runs the code. Fuzzing explores the input space automatically; property‑based testing turns specifications into executable predicates; differential testing uses a known‑good implementation as an oracle. Coverage feedback can be fed back to the model to improve future generations (see C3 on complexity backpressure).

## 8. Mutation testing for AI‑generated code

- Inject small syntactic changes into generated code
- Run test suite; surviving mutants indicate weak tests
- Helps measure test adequacy beyond coverage
- Can be automated in CI pipelines

**Notes** (5 min · outcomes CO4.LO1 · sources [C3]): Mutation testing evaluates the quality of the test suite itself. By systematically mutating the generated code (e.g., flipping operators, changing constants) and checking whether tests fail, we learn whether the tests would catch real defects. This is especially valuable for AI code where the test suite may also be generated.

## 9. Learned evaluators: LLM‑as‑judge and reward models

- LLM‑as‑judge: a separate model scores candidate outputs
- Reward models predict human preference or quality signals
- They estimate style, readability, or adherence to instructions
- Functional correctness still requires execution‑based tests

**Notes** (5 min · outcomes CO4.LO1 · sources [C1] [C6]): Learned evaluators are useful for ranking many candidates quickly. A reward model is trained on human feedback and predicts which output a person would prefer. However, it does not execute code, so it cannot reliably certify functional correctness. Execution‑based tests remain the ground truth for correctness; reward models complement them by filtering obvious low‑quality samples.

## 10. Evaluation metrics for code generation

- Pass@k: probability that at least one of k samples passes hidden tests
- Syntax correctness: fraction of parsable programs
- Semantic similarity: e.g., CodeBLEU, execution match
- Runtime performance: latency, memory within limits

**Notes** (5 min · outcomes CO4.LO1 · sources [C1]): Pass@k is the standard metric in code generation benchmarks (C1). It is defined as the probability that at least one of k independently sampled candidates passes the hidden test suite. The unbiased estimator counts, for each problem, how many of the k samples pass and applies the formula 1 - C(n‑c, k) / C(n, k) where n is total samples and c is passing samples. Syntax and semantic metrics give complementary views.

## 11. Computing Pass@k from sample results (illustrative) (Example)

- Problem: 100 samples generated, 30 pass hidden tests
- k = 10, n = 100, c = 30
- Pass@10 = 1 - C(70,10)/C(100,10) ≈ 0.96
- Numbers are illustrative; real benchmarks use many problems

**Notes** (6 min · outcomes CO4.LO1 · sources [C1]): This table walks through the unbiased estimator for Pass@k. With 100 generated samples and 30 that pass, the chance that a random set of 10 contains at least one passing sample is about 96%. The calculation uses combinatorics; in practice libraries compute it directly. The figures are purely illustrative to show the mechanics.

## 12. Benchmark suites for code generation

- HumanEval: 164 Python problems with unit tests
- MBPP: 974 basic programming problems
- APPS: 10,000 problems from easy to competition level
- Benchmarks enable reproducible comparison of models and pipelines

**Notes** (5 min · outcomes CO4.LO1 · sources [C1] [C4]): Standard benchmarks provide a common ground for evaluating code generation. HumanEval and MBPP focus on functional correctness; APPS adds algorithmic difficulty. When reporting Pass@k or other metrics, always state the benchmark and the exact evaluation protocol (temperature, number of samples, test suite version).

## 13. Reliability requirements and test adequacy criteria

- Safety‑critical: require mutation score > 90% and zero critical mutants
- Business‑critical: target Pass@k ≥ 0.95 on representative benchmarks
- Regulatory: traceability from requirement to test case
- Adequacy criteria guide where to invest testing effort

**Notes** (5 min · outcomes CO4.LO1 · sources [C4]): Different domains impose different reliability targets. Safety‑critical systems often mandate high mutation scores and evidence that all requirements are exercised. Business‑critical AI services may set a Pass@k threshold on a curated benchmark. Explicit adequacy criteria turn vague quality goals into measurable testing objectives.

## 15. Check: Pass@k definition (Check)


**What does Pass@k measure in code generation evaluation?**

A. The fraction of generated programs that compile successfully
B. The probability that at least one of k sampled candidates passes the hidden tests
C. The average similarity score between generated and reference solutions
D. The percentage of test cases covered by the generated code

*Answer: B. The probability that at least one of k sampled candidates passes the hidden tests. Pass@k is defined as the probability that at least one of k independently sampled candidates passes the hidden test suite. Option 0 describes syntax correctness, option 2 describes semantic similarity metrics like CodeBLEU, and option 3 describes test coverage. The most tempting wrong answer is option 0 because compilation is a prerequisite but not the definition of Pass@k.*

**Notes** (4 min · outcomes CO4.LO1): This question checks the precise definition of Pass@k, a core metric for the learning outcome. The explanation clarifies why the other options are related but distinct concepts.

## 16. Check: Role of reward models (Check)


**Which statement best describes the role of a reward model in AI code generation pipelines?**

A. It executes generated code and reports pass/fail results
B. It predicts human preference or quality signals without running the code
C. It formally verifies that the code satisfies a given specification
D. It mutates the code to assess test suite adequacy

*Answer: B. It predicts human preference or quality signals without running the code. Reward models are trained on human feedback to predict which outputs humans would prefer; they do not execute code, perform formal verification, or conduct mutation testing. Option 0 describes execution‑based testing, option 2 describes static specification checking, and option 3 describes mutation testing. The most tempting wrong answer is option 0 because both reward models and execution tests are used for quality assessment, but they operate differently.*

## 17. Summary: Automated testing and evaluation mechanisms (Summary)

- Static spec checks catch contract violations early
- Dynamic testing (fuzzing, property‑based, differential) validates runtime behavior
- Mutation testing measures test suite quality
- Learned evaluators rank candidates but cannot replace execution tests
- Pass@k and benchmark suites provide standardized effectiveness metrics
- Reliability requirements drive adequacy criteria and pipeline design

**Notes** (5 min · outcomes CO4.LO1): Recap the main mechanisms: static specification‑driven verification, dynamic execution‑based testing, mutation analysis, learned evaluators, and quantitative metrics. Emphasize that each mechanism addresses different reliability requirements and that a robust AI‑native pipeline combines them in a layered fashion. This summary directly supports CO4.LO1.
