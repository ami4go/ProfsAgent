## 4. Testing Mechanisms Overview

- Unit tests for deterministic code
- Model evaluation tests for accuracy
- Pipeline integration tests for end-to-end flow
- Contract tests for service interfaces

**Notes** (5 min · outcomes CO4.LO1): Introduce four main testing mechanisms used in AI-native pipelines. Unit tests cover traditional code. Model evaluation tests assess predictive performance on held-out data. Pipeline integration tests verify that data flows correctly through preprocessing, inference, and postprocessing. Contract tests ensure that service APIs meet agreed schemas.

## 5. Unit Testing for AI Components

- Test data preprocessing functions
- Test feature engineering logic
- Test model wrapper error handling
- Mock external model APIs

**Notes** (5 min · outcomes CO4.LO1): Explain that unit tests for AI components focus on deterministic transformations: data cleaning, feature extraction, and wrapper logic. Mocking external model endpoints isolates tests from network latency and model version changes. This keeps unit tests fast and reliable.

## 6. Integration Testing for Pipelines

- Validate data schema compatibility
- Check model version rollout
- Verify monitoring hooks
- Test rollback procedures

**Notes** (5 min · outcomes CO4.LO1): Integration tests exercise the full pipeline from raw input to final output. They check that schema contracts between stages hold, that new model versions can be deployed without breaking downstream stages, and that observability hooks (metrics, logs) fire correctly. Include rollback tests to ensure safe recovery.

## 7. Evaluation Metrics for AI Models

- Accuracy, precision, recall for classification
- RMSE, MAE for regression
- Calibration error for probability outputs
- Latency and throughput for serving

**Notes** (5 min · outcomes CO4.LO1): List common model-level metrics. Classification tasks use accuracy, precision, recall, F1. Regression tasks use RMSE, MAE. Calibration error measures how well predicted probabilities match true frequencies. Serving metrics like latency and throughput are critical for production SLAs.

## 8. Why Pipeline Evaluation Matters

- Model metrics alone miss system failures
- Data drift can degrade downstream stages
- Resource constraints affect reliability
- End-to-end metrics guide release decisions

**Notes** (5 min · outcomes CO4.LO1): Explain that evaluating only the model is insufficient. Pipeline evaluation captures issues like data drift, schema mismatches, and resource bottlenecks that only appear when components interact. End-to-end metrics such as pipeline success rate and end-to-end latency inform go/no-go release decisions.

## 9. Pipeline Evaluation Mechanisms

- Automated canary deployments
- Shadow traffic mirroring
- Synthetic data probes
- Continuous evaluation dashboards

**Notes** (10 min · outcomes CO4.LO1): Describe mechanisms to evaluate pipelines in production. Canary deployments route a small fraction of traffic to new pipeline versions. Shadow mirroring runs new pipeline alongside current without affecting users. Synthetic probes inject known inputs to detect regressions. Dashboards aggregate metrics for continuous visibility.

## 10. Metric Categories: Reliability, Performance, Quality

- Reliability: success rate, MTBF, flakiness
- Performance: latency, throughput, resource use
- Quality: prediction accuracy, drift detection
- Operational: deployment frequency, rollback time

**Notes** (10 min · outcomes CO4.LO1): Group pipeline metrics into four categories. Reliability metrics measure how often the pipeline completes without error (success rate, mean time between failures, flakiness). Performance metrics capture speed and resource consumption. Quality metrics track model prediction health and data drift. Operational metrics reflect process health.

## 13. Check: Testing Mechanism Comparison (Check)


**Which testing mechanism is best suited for verifying that a new model version does not break downstream pipeline stages?**

A. Unit tests for model wrapper
B. Model evaluation tests on held-out data
C. Pipeline integration tests
D. Contract tests for service interfaces

*Answer: C. Pipeline integration tests. Pipeline integration tests exercise the full flow from data ingestion through model inference to downstream consumers, making them the right choice for catching breakages across stages. Unit tests and model evaluation tests are too narrow, while contract tests only check interface compliance, not functional correctness.*

**Notes** (5 min · outcomes CO4.LO1): Ask students to select the best answer. Discuss why integration tests are the correct choice and why the other options are insufficient for this specific goal.

## 14. Check: Reliability Metric Choice (Check)


**A team wants to measure how often a pipeline stage fails intermittently despite automatic retries. Which reliability metric should they track?**

A. Mean time between failures (MTBF)
B. Stage success rate
C. Flakiness rate
D. Rollback frequency

*Answer: C. Flakiness rate. Flakiness rate directly captures the frequency of intermittent failures that succeed on retry. MTBF measures time between any failures, not specifically intermittent ones. Stage success rate aggregates all outcomes, and rollback frequency reflects deployment issues, not stage flakiness.*

**Notes** (5 min · outcomes CO4.LO1): Highlight that flakiness rate is the metric designed for intermittent failures. Clarify the distinction between MTBF and flakiness.

## 15. Common Pitfalls in Pipeline Evaluation

- Relying solely on model accuracy
- Ignoring data schema evolution
- Overlooking resource saturation
- Skipping rollback validation

**Notes** (5 min · outcomes CO4.LO1): Summarize frequent mistakes: focusing only on model-level metrics while missing system-level failures; not testing schema changes that break downstream stages; not monitoring CPU/GPU/memory under load; and not practicing rollback procedures, leading to prolonged outages.
