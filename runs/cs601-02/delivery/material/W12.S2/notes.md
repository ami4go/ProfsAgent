- SLO = target threshold for SLI
- Examples: latency <200 ms, error rate <0.1%

| SLI | SLO example |
|---|---|

## 6. Error budgets and burn rate

- Error budget = 1 – SLO
- Burn rate = budget consumed / time
- High burn rate triggers alerts

Budget allocated → Consumption measured → Burn rate computed → Alert if > threshold

*Error budget lifecycle*

**Notes** (5 min · outcomes CO4.LO3 · sources [C3] [C6]): Error budget quantifies how much unreliability is tolerable before the SLO is violated. Burn rate expresses how fast that budget is being spent. A burn rate above 1× means the budget will be exhausted before the window ends; 2× or higher is a common alert threshold. This concept underpins automated rollback policies.

## 9. Evaluating supplied project metrics step‑by‑step (Worked problem)

- Load per‑service SLI logs
- Compute SLO compliance per service
- Calculate remaining error budget safely

```python
def evaluate_service(logs, slo_target):
    if not logs:
        return {'compliance': None, 'budget_remaining': None, 'note': 'no observations'}
    bad = sum(1 for e in logs if e['latency_ms'] > slo_target['latency_ms'] or e['error'])
    total = len(logs)
    compliance = 1 - bad / total
    max_err = slo_target.get('max_error_rate', 0.001)
    if max_err <= 0:
        budget = None
    else:
        budget = max(0, (max_err - bad/total) / max_err)
    return {'compliance': compliance, 'budget_remaining': budget}
```

*Safe metric evaluation snippet*

**Notes** (12 min · outcomes CO4.LO3 · sources [C2] [C3]): Demonstrate a robust evaluation routine that guards against empty log lists (avoiding division by zero) and validates that the SLO’s permitted error rate is positive before computing a budget ratio. Show how the function returns a clear ‘no observations’ marker instead of crashing. This mirrors the safe‑coding practices required for automated rollback pipelines.

## 11. Check: Error budget calculation (Check)


**A service has an SLO of 99.9% availability over a 30‑day window. After 15 days it has experienced 0.05% downtime. What is the remaining error budget as a fraction of the total budget?**

A. 0.50
B. 0.75
C. 0.25
D. 0.90

*Answer: B. 0.75. Total error budget = 0.1% of 30 days = 0.03 day‑equivalents. Consumed = 0.05% of 15 days = 0.0075 day‑equivalents. Remaining = 0.03 - 0.0075 = 0.0225, which is 75% of the total budget. Option A (0.50) incorrectly assumes linear time scaling without accounting for the SLO percentage.*

**Notes** (4 min · outcomes CO4.LO3): This question tests the ability to compute error‑budget consumption proportionally. The most tempting wrong answer (0.50) comes from assuming half the time means half the budget, ignoring the SLO’s percentage definition.

## 12. Check: Burn rate interpretation (Check)


**If a service’s error budget is being consumed at a burn rate of 2.5×, what does this indicate about the remaining budget?**

A. Budget will last the full window
B. Budget will be exhausted before the window ends
C. Budget is increasing
D. Burn rate is irrelevant to budget

*Answer: B. Budget will be exhausted before the window ends. A burn rate > 1× means the budget is being spent faster than the window’s duration allows; at 2.5× the budget will run out well before the window closes. Option A is the common misconception that any burn rate below 10× is safe.*

**Notes** (4 min · outcomes CO4.LO3): Reinforces the operational meaning of burn rate. Students often confuse burn‑rate magnitude with absolute safety; the key is the ratio to 1×.

## 14. Alerting and automated rollback policies

- Define burn‑rate thresholds
- Link alerts to CI/CD rollback
- Prevent cascade failures

| Policy | Trigger |
|---|---|
| Fast burn | Burn rate > 2× |
| Slow burn | Budget < 10% |

*Example rollback policies*

**Notes** (4 min · outcomes CO4.LO3 · sources [C3] [C6]): Two common policy tiers: a fast‑burn alert (e.g., >2×) triggers immediate rollback; a slow‑burn alert (budget below 10%) pauses further releases and notifies on‑call. Both are wired into the CI/CD system so that a failing deployment cannot propagate to downstream services.

## 15. Common pitfalls in metric evaluation

- Dividing by zero on empty logs
- Ignoring cold‑start latency spikes
- Treating all errors equally

**Notes** (4 min · outcomes CO4.LO3 · sources [C2] [C3]): Highlight three frequent bugs: (1) naive division by len(logs) when a service has no traffic yet; (2) including cold‑start requests in latency SLIs, which inflates p99; (3) counting harmless validation errors the same as safety‑filter rejections. The worked problem earlier demonstrates a guard against the first pitfall.
