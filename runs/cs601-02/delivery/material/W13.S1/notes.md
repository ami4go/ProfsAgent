## 4. Core Deployment Metrics for Multi-Component Systems

- Latency percentiles (p50, p95, p99)
- Throughput (requests/second)
- Error rates by type
- Rollback frequency and duration
- Resource saturation indicators

| Metric | Target | Collection Method |
|---|---|---|
| Latency p99 | <500ms | Prometheus histogram |
| Throughput | >1000 req/s | Counter increments |
| Error rate | <0.5% | Counter by type |
| Rollback frequency | <1/week | Deployment logs |
| CPU saturation | <80% | Node exporter |

*Key deployment metrics and collection methods*

**Notes** (5 min · outcomes CO4.LO3 · sources [C3]): Deployment metrics must be collected per component and aggregated. Latency percentiles reveal tail latency issues. Throughput indicates capacity. Error rates categorized by HTTP codes, model errors, timeouts. Rollback frequency shows deployment stability. Resource saturation (CPU, GPU, memory) predicts failures.

## 5. Reliability Metrics: MTBF, MTTR, Availability, SLOs

- Mean Time Between Failures (MTBF)
- Mean Time To Recovery (MTTR)
- Availability = MTBF/(MTBF+MTTR)
- Service Level Objectives (SLOs) and Indicators (SLIs)
- Error budgets for release decisions

Define SLIs → Set SLOs → Measure → Alert on error budget burn → Automate rollback

*SLO-driven reliability loop*

**Notes** (5 min · outcomes CO4.LO3 · sources [C6]): Reliability metrics quantify system health over time. MTBF and MTTR are classic. SLOs translate business requirements into measurable targets (e.g., 99.9% requests <200ms). Error budgets allow balancing feature velocity vs reliability. These metrics guide automated deployment decisions.

## 13. Check: Metric Selection for AI Model Serving (Check)


**Which metric is most critical for detecting model serving performance degradation in real-time?**

A. CPU utilization of the model server
B. Prediction latency p99
C. Number of model parameters
D. Training loss on validation set

*Answer: B. Prediction latency p99. Prediction latency p99 directly reflects user-facing performance. CPU utilization is a resource metric but doesn't guarantee latency SLOs. Model parameters and training loss are offline metrics, not deployment metrics.*

**Notes** (3 min · outcomes CO4.LO3): This check assesses understanding of deployment vs offline metrics. The most tempting wrong answer is CPU utilization because it's commonly monitored but doesn't capture tail latency.

## 14. Check: Reliability Evaluation Decision (Check)


**During a canary deployment, the error budget burn rate exceeds 10x. What is the correct automated action?**

A. Increase canary traffic to 100%
B. Pause deployment and alert on-call
C. Rollback canary to previous version
D. Ignore and continue monitoring

*Answer: C. Rollback canary to previous version. A burn rate >10x indicates rapid error budget consumption. Automated rollback protects users. Pausing and alerting is slower. Increasing traffic worsens impact. Ignoring violates SLO commitments.*

**Notes** (3 min · outcomes CO4.LO3): This check tests knowledge of error budget policies and automated remediation. The tempting wrong answer is pausing and alerting, which is manual and slower than automated rollback.
