## 5. Core Deployment Metrics: Definitions and Targets

- Latency: p50, p95, p99 per component and end-to-end
- Throughput: requests/sec, tokens/sec, batch size
- Error rate: HTTP 5xx, model exceptions, validation failures
- Availability: uptime %, SLA adherence, degradation minutes
- Resource utilization: GPU/CPU, memory, network, cost per request

| Metric | Scope | Typical Target | Collection Method |
|---|---|---|---|
| Latency (p99) | End-to-end | < 2s | Distributed tracing |
| Throughput | Per replica | > 100 req/s | Prometheus counters |
| Error rate | Service | < 0.1% | Structured logging |
| Availability | System | 99.9% | Health checks |
| Cost per 1k tokens | Model | < $0.002 | Billing API |

## 6. Reliability Metrics: From MTBF to SLOs

- MTBF: mean time between failures (system-level)
- MTTR: mean time to recover (incident response)
- SLI: service level indicator (quantifiable measure)
- SLO: service level objective (target for SLI)
- Error budget: inverse of SLO, guides release velocity

| Metric | Definition | Example | Used For |
|---|---|---|---|
| MTBF | Average uptime between failures | 720 hours | Capacity planning |
| MTTR | Average repair time | 15 minutes | On-call readiness |
| SLI | Measurable behavior | Request latency < 500ms | Monitoring |
| SLO | Target for SLI | 99% of requests < 500ms | Alerting |
| Error budget | 1 - SLO | 1% error allowance | Release gating |

*Reliability metrics hierarchy and relationships*

**Notes** (7 min · outcomes CO4.LO3 · sources [C3] [C4]): Define each term and show how they form a hierarchy: SLIs are measured, SLOs are set, error budgets are consumed. MTBF/MTTR are operational outcomes. For AI-native systems, SLIs must include model quality signals (e.g., correctness rate). Cite C3 on complexity backpressure: as AI agent complexity grows, MTTR increases without proper observability.

## 7. Evaluating Metrics in Multi-Component AI Pipelines

- Correlate metrics across service boundaries
- Identify bottleneck components via latency breakdown
- Aggregate error budgets across dependent services
- Detect cascading failures from model drift
- Use distributed tracing and unified dashboards

Collect per-component metrics → Correlate via trace IDs → Compute end-to-end SLIs → Compare against SLOs → Trigger alerts or rollback

*Metric evaluation pipeline for multi-component system*

Explain how error budgets propagate: if the model server consumes 80% of the latency budget, the retriever must stay within 20%. ## 8. Scenario 1: Evaluating a RAG Chatbot Deployment (Worked problem)

- System: API gateway → embedding service → vector DB → LLM
- Given: p99 latency 3.2s (SLO 2s), error rate 0.5% (SLO 0.1%)
- Step 1: Break down latency per component via traces
- Step 2: Identify vector DB p99 = 1.8s (bottleneck)
- Step 3: Check error budget: 0.5% > 0.1% → freeze releases
- Step 4: Propose fix: add read replicas, cache frequent queries

```python
traces = fetch_traces(service='rag', window='1h')
latencies = {}
for trace in traces:
    for span in trace.spans:
        latencies.setdefault(span.service, []).append(span.duration)
for svc, vals in latencies.items():
    print(f'{svc}: p99={np.percentile(vals,99):.2f}s')
```

*Pseudo-code for latency breakdown analysis*

Show how to query distributed traces (e.g., Jaeger, Zipkin) to get per-component latency distributions. Identify the vector DB as the bottleneck. Explain that error budget exhaustion triggers a release freeze per SRE practice. Propose mitigations and how to verify they restore SLO compliance. ## 9. Scenario 2: Evaluating a Code Generation Pipeline (Worked problem)

- System: spec parser → planner → code generator → test runner
- Given: MTTR 45 min (target 15 min), test flakiness 12%
- Step 1: Analyze incident logs for root cause categories
- Step 2: Find 60% of MTTR spent in manual triage
- Step 3: Flakiness correlates with LLM non-determinism
- Step 4: Propose: automated classification, seeded generation, retries

```python
results = load_test_runs(pipeline='codegen', days=7)
flaky = []
for test, runs in results.groupby('test_id'):
    outcomes = runs['status'].unique()
    if len(outcomes) > 1:
        flaky.append(test)
print(f'Flaky tests: {len(flaky)} ({len(flaky)/len(results):.1%})')
# Classify failure reasons
for test in flaky:
    failures = runs[runs['status']=='fail']
    print(test, failures['error_type'].value_counts())
```

*Flakiness detection and classification snippet*

## 11. Check: Deployment Metric Selection (Check)


**Which metric is MOST appropriate for capturing the user-perceived responsiveness of an LLM-based chat endpoint?**

A. Average CPU utilization of the model server
B. p99 end-to-end latency including token generation
C. Number of GPU instances running
D. Training loss of the underlying model

*Answer: B. p99 end-to-end latency including token generation. p99 end-to-end latency directly measures the worst-case user experience, including token streaming delays. CPU utilization and GPU count are infrastructure metrics, not user-facing. Training loss is a model development metric, not a deployment metric.*

**Notes** (5 min · outcomes CO4.LO3): Quick check to ensure students distinguish user-facing latency metrics from infrastructure and model metrics. The most tempting wrong answer is average CPU utilization because it's commonly monitored but doesn't reflect tail latency.

## 12. Check: Reliability Metric Relationships (Check)


**If a service has an SLO of 99.9% availability over 30 days, what is its error budget in minutes?**

A. 43.2 minutes
B. 4.32 minutes
C. 432 minutes
D. 0.432 minutes

*Answer: A. 43.2 minutes. 30 days = 43,200 minutes. 0.1% of 43,200 = 43.2 minutes. The error budget is the allowed downtime. 4.32 minutes would be for 99.99% (four nines). 432 minutes is 1% (two nines). 0.432 minutes is 0.001% (five nines).*

**Notes** (5 min · outcomes CO4.LO3): Tests understanding of error budget calculation. Common mistake: confusing percentage with decimal (0.1% vs 0.1). Also confusing days to minutes conversion.

## 13. Best Practices for Continuous Metric Evaluation

- Automate SLO dashboards and alerting on error budget burn rate
- Include model quality SLIs (correctness, hallucination rate)
- Run synthetic canary requests every minute
- Correlate deployments with metric shifts using change events
- Review and adjust SLOs quarterly with stakeholders

**Notes** (5 min · outcomes CO4.LO3 · sources [C4]): Summarize operational practices: burn-rate alerting (fast vs slow burn), adding model-specific SLIs, synthetic monitoring to detect silent failures, deployment correlation for rapid rollback, and periodic SLO recalibration. Reference C4 on the need for new evaluation frameworks in generative AI.

## 14. Common Pitfalls in Metric Evaluation

- Averaging percentiles (p99 of averages != average of p99)
- Ignoring cold-start latency in serverless model endpoints
- Using only aggregate metrics, missing per-tenant SLOs
- Setting SLOs without historical baseline data
- Alerting on raw metrics instead of error budget burn

**Notes** (5 min · outcomes CO4.LO3 · sources [C3] [C4]): Highlight frequent mistakes: percentile math errors, cold starts in AI model servers (GPU initialization), multi-tenancy requiring per-customer SLOs, arbitrary SLOs leading to constant paging, and noisy alerts. Emphasize that AI-native systems amplify these due to variable token generation times and model loading.
