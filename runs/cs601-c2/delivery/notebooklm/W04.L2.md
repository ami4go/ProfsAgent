## 2 · Course context (paste as a text source)

```text
COURSE: Software Development using AI (IIIT-Delhi, level 3xx, 3/4-year B.Tech students)
LECTURE: W04.L2 · week 4 · Standards and specification guidelines for use cases (120 minutes)

LEARNING OUTCOMES (what students must be able to do):
- Outline use cases and system boundaries from unstructured product descriptions using standards and specification guidelines for most short items.

THIS LECTURE, PART BY PART:
1. The Need for Standardized Use Case Specifications (10 min, concept)
   Teaches: Students will understand why unstructured product descriptions lead to scope creep and misinterpretation in software projects. They will identify standard use case components necessary for transforming raw ideas into precise functional specifications.
   Key terms: unstructured product description, use case specification, scope creep, system requirements, ISO/IEC/IEEE 29148
2. Defining System Boundaries and Primary vs. Secondary Actors (15 min, mechanism)
   Teaches: Students will learn how to construct clear system boundaries that separate internal automated behaviors from external user actions. They will classify primary actors, secondary supporting actors, and external third-party systems from informal text.
   Key terms: system boundary, primary actor, secondary actor, external system, scope definition
3. Standard Templates for Brief and Fully Dressed Use Cases (15 min, concept)
   Teaches: Students will compare standard use case templates, including Cockburn's casual and fully dressed formats. They will learn the mandatory fields required to document a use case brief concisely and unambiguously.
   Key terms: Cockburn template, brief format, fully dressed format, use case goal, level of detail
4. Extracting Use Cases from Unstructured Narrative Text (20 min, mechanism)
   Teaches: Students will apply a step-by-step heuristic to extract actor-goal pairs from informal user feedback and feature requests. They will learn how to filter out UI implementation details while retaining core functional requirements.
   Key terms: actor-goal list, textual parsing, heuristics, domain interaction, narrative extraction
5. Formulating Main Success Scenarios with Strict Writing Guidelines (15 min, mechanism)
   Teaches: Students will learn standard grammatical rules for writing Main Success Scenario steps, such as using subject-verb-object structure, active voice, and explicit actor naming. They will convert informal step descriptions into standardized, sequential action steps.
   Key terms: Main Success Scenario, active voice, Subject-Verb-Object, step sequencing, specification guidelines
6. Worked Example: Converting a Raw Feature Prompt to Use Case Outlines (20 min, worked example)
   Teaches: Students will watch the step-by-step transformation of a multi-paragraph, messy product description for an e-commerce checkout into formal use case outlines. They will observe how to resolve ambiguous phrases, split compound goals, and establish system boundaries explicitly.
   Key terms: worked example, raw description, use case outline, boundary clarification, goal splitting
7. Specifying Preconditions, Guarantees, and Extension Branches (15 min, mechanism)
   Teaches: Students will learn how to formalize entry preconditions, minimal and success guarantees, and exception handling branches in standard use case documentation. They will evaluate trade-offs between detail level and specification maintainability.
   Key terms: precondition, minimal guarantee, success guarantee, extension branch, exception flow
8. Evaluating Use Case Quality and Completeness Checklist (10 min, discussion)
   Teaches: Students will analyze sample use case outlines against a standard quality checklist to detect boundary leaks, missing actors, and untestable steps. They will discuss how standardized specifications reduce downstream errors in AI-assisted development.
   Key terms: quality checklist, testability, boundary leak, ambiguity detection, specification review

COMES LATER (do not teach here):
- Software requirements and requirements engineering (week 4)
```
