## 2 · Course context (paste as a text source)

```text
COURSE: Software Development using AI (IIIT-Delhi, level 3xx, 3/4-year B.Tech students)
LECTURE: W10.L1 · week 10 · Testing and validation in iterative development (90 minutes)

LEARNING OUTCOMES (what students must be able to do):
- Analyze execution traces produced by coding agents during iterative loop engineering tasks, for a supplied log file of at most 2000 lines, identifying at least three distinct failure causes with supporting log evidence.

STUDENTS ALREADY KNOW:
- Software factories and execution trace analysis (week 9)
- Trace structure and metadata (earlier lecture on this topic)
- Worked example: diagnosing tool misuse (earlier lecture on this topic)

THIS LECTURE, PART BY PART:
1. Log parsing and query techniques (15 min, demo)
   Teaches: Students practice using grep, jq, and awk to filter a 2000-line trace for specific event types, extract timestamps, and count occurrences of error codes. They learn to build reusable one‑liners for rapid evidence gathering.
   Key terms: grep, jq, awk, filter, extraction, one-liner
2. Systematic trace analysis workflow (15 min, mechanism)
   Teaches: A step‑by‑step method is introduced: (1) segment the trace by iteration, (2) hypothesize failure categories, (3) search for signature patterns, (4) collect supporting lines, (5) validate each hypothesis against the code context. Students apply the workflow to a short trace.
   Key terms: segmentation, hypothesis, signature_pattern, validation, code_context
3. Worked example: multi-failure trace analysis (15 min, worked example)
   Teaches: The instructor analyses a full 2000-line trace containing three distinct failures: a permission error, a version mismatch, and a logic loop. For each failure, the exact log lines are highlighted and linked to the underlying cause.
   Key terms: permission_error, version_mismatch, logic_loop, evidence_linking, distinct_failures
4. Activity: pair analysis of new trace (15 min, activity)
   Teaches: In pairs, students receive a fresh 1500-line trace and must identify at least three failure causes, citing line numbers and error codes. They prepare a brief report and present findings to the class for peer review.
   Key terms: pair_work, fresh_trace, line_numbers, error_codes, peer_review
5. Comparison of analysis strategies (15 min, comparison)
   Teaches: Students compare manual trace inspection, scripted querying, and LLM‑assisted summarisation. They evaluate speed, accuracy, and false‑positive rates on the same trace, discussing when each approach is preferable.
   Key terms: manual_inspection, scripted_query, LLM_assisted, false_positive, trade_off
6. Discussion: validation and reporting findings (15 min, discussion)
   Teaches: The class discusses how to validate identified causes (re‑run, unit test, stakeholder confirmation) and how to structure a concise failure report for developers. Emphasis is placed on actionable recommendations and traceability back to log evidence.
   Key terms: validation, re_run, unit_test, stakeholder_confirmation, failure_report, traceability
```
