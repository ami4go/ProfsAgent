## 2 · Course context (paste as a text source)

```text
COURSE: Software Development using AI (IIIT-Delhi, level 3xx, 3/4-year B.Tech students)
LECTURE: W05.L1 · week 5 · Software requirements and requirements engineering (150 minutes)

LEARNING OUTCOMES (what students must be able to do):
- Outline use cases and system boundaries from unstructured product descriptions using spec-driven development guidelines.

STUDENTS ALREADY KNOW:
- Standards and specification guidelines for use cases (week 4)
- Recap use case standards and spec guidelines (earlier lecture on this topic)
- Identify actors and system boundaries (earlier lecture on this topic)

THIS LECTURE, PART BY PART:
1. Extract functional requirements from description (15 min, worked example)
   Teaches: Using a worked example, students parse an unstructured product description to list functional requirements, grouping them by user goal. They apply a template to capture preconditions, postconditions, and triggers.
   Key terms: functional requirement, user goal, precondition, postcondition, trigger, template
2. Write use case main success scenario (15 min, mechanism)
   Teaches: Students construct the main success scenario for a use case, writing numbered steps that show actor–system interactions. They ensure each step is atomic, observable, and follows the spec guidelines.
   Key terms: main success scenario, actor–system interaction, atomic step, observable, spec guidelines
3. Write use case extensions and alternate flows (15 min, mechanism)
   Teaches: Students extend the main scenario with extension points, alternate flows, and exception handling, using the same numbering scheme. They learn to reference extension conditions and maintain traceability.
   Key terms: extension point, alternate flow, exception handling, traceability, numbering scheme
4. Create system boundary context diagram (15 min, demo)
   Teaches: In a live demo, the instructor builds a UML context diagram showing the system, actors, and external systems. Students see how the diagram validates the actor list and boundary decisions.
   Key terms: context diagram, UML, system boundary, external system, actor validation
5. Prioritize use cases with MoSCoW (15 min, comparison)
   Teaches: Students compare MoSCoW, business value, and risk‑based prioritization techniques on a sample use case set. They decide which use cases belong to Must, Should, Could, Won't for the first release.
   Key terms: MoSCoW, business value, risk‑based, prioritization, release planning
6. Validate use cases against spec guidelines (15 min, discussion)
   Teaches: Through guided discussion, students apply a checklist derived from spec‑driven guidelines to assess completeness, consistency, and testability of their use cases. They identify missing preconditions and ambiguous steps.
   Key terms: checklist, completeness, consistency, testability, ambiguity
7. Map use cases to spec-driven framework artifacts (15 min, concept)
   Teaches: Students learn how each use case maps to downstream artifacts such as feature files, acceptance criteria, and test cases in a spec‑driven development framework. They trace a use case through the pipeline.
   Key terms: feature file, acceptance criteria, test case, traceability, pipeline
8. Case study: product description to use case model (15 min, case study)
   Teaches: A full case study walks through transforming a realistic product description into a complete use case model, including actors, boundary, scenarios, and prioritization. Students analyse each transformation decision.
   Key terms: case study, transformation, use case model, decision analysis, realistic example
9. Common pitfalls and quality checklist (15 min, discussion)
   Teaches: Discussion of frequent errors such as actor overload, vague steps, and missing extensions. Students use a quality checklist to review a peer's use case specification and suggest improvements.
   Key terms: actor overload, vague step, missing extension, quality checklist, peer review
10. Summary and transition to spec-driven frameworks (15 min, concept)
   Teaches: Recap of the use case engineering process, emphasizing how the produced artifacts feed into spec‑driven development frameworks. Students outline next steps for automated test generation.
   Key terms: recap, spec‑driven framework, automated test generation, next steps, artifact flow

COMES LATER (do not teach here):
- Spec-driven development frameworks (week 5)
```
