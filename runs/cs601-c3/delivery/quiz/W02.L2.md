# Review quiz · W02.L2 · Coding agents and context engineering

## Recap of the previous lecture (5 min)

1. How do resources differ from tools in Model Context Protocols (MCP)?
   - A. Resources provide passive context data for reading, whereas tools enable dynamic side-effects and execution.
   - B. Resources allow models to execute shell commands, whereas tools only provide static files.
   - C. Resources require dynamic parameters, whereas tools do not accept input arguments.
   - D. Resources are defined on the host client, whereas tools reside exclusively on external cloud services.

2. A developer wants to expose dynamic log streams where the log file URI changes based on a requested user ID parameter. Which MCP construct should they use?
   - A. An environment variable override in the host workspace setting
   - B. A fixed text resource without dynamic URI mapping
   - C. A static tool definition with hardcoded execution parameters
   - D. A parameterized Resource Template with a dynamic URI scheme

3. How does an MCP host validate arguments provided by an LLM before invoking a tool via `tools/call`?
   - A. It validates arguments against the `inputSchema` declared in the server's `tools/list` response.
   - B. It relies on the server to bypass validation if the connection uses stdio.
   - C. It converts all input values to strings automatically without schema checks.
   - D. It forwards the raw prompt to a manual host validation queue.

## Review quiz (5 min)

1. What is the primary role of an architectural scratchpad during an autonomous coding agent's execution lifecycle?
   - A. It tracks short-term state, intermediate reasoning steps, and tool observation outputs across loop iterations.
   - B. It automatically compiles static analysis binaries inside container sandboxes.
   - C. It bypasses permission checks when the agent executes shell commands.
   - D. It permanently stores global system environment variables across project sessions.

2. Why would a developer implement selective file tree pruning when building a prompt context for a coding agent?
   - A. To allow MCP tools to run without requiring input parameter validation.
   - B. To guarantee that all unit tests pass before tool dispatch occurs.
   - C. To prevent model distraction and avoid exceeding context window token budgets by filtering out irrelevant directories.
   - D. To permanently delete legacy files from the local Git repository.

3. A custom MCP tool for linting files frequently fails because the agent passes invalid parameter data types. How should the tool definition be updated to resolve this according to MCP specifications?
   - A. Switch the workspace isolation model from container sandboxing to a local git worktree.
   - B. Define explicit JSON schema types and parameter validation rules in the tool's input descriptor.
   - C. Enable sliding context windows to prune past tool validation errors.
   - D. Inject the full static analysis output directly into the global prompt context.

4. A system loading 100+ verbose MCP tool definitions into every prompt suffers from high latency and hallucinated tool invocations. How does lazy tool registration mitigate this context pollution issue compared to global tool injection?
   - A. By bypassing environment sandboxing to execute static analysis directly on the host.
   - B. By replacing JSON-RPC schemas with lightweight hardcoded shell scripts.
   - C. By dynamic-loading schema descriptors only when relevant sub-tasks are identified, lowering token overhead and tool confusion.
   - D. By running all tool executions in parallel without waiting for agent observation loops.

## Answers

- Recap 1: **A**: Resources act as passive data providers (like context or read-only files), while tools allow models to run dynamic operations and side-effects. (W02.L1.C1)
- Recap 2: **D**: Resource templates expose parameterized URI schemes, allowing clients to construct dynamic URIs to read specific dynamic context. (W02.L1.C2)
- Recap 3: **A**: Tools define their input requirements via standard JSON Schema (`inputSchema`) during discovery (`tools/list`), which allows strict client/server argument validation. (W02.L1.C3)
- Quiz 1: **A**: The scratchpad functions as short-term memory within the agent lifecycle loop, enabling the model to retain intermediate context, track progress, and consume tool observations before taking the next action. (W02.L2.C1)
- Quiz 2: **C**: Pruning irrelevant directories and files reduces context pollution and keeps token usage within limits, preventing the LLM from getting distracted by unrelated codebase noise. (W02.L2.C2)
- Quiz 3: **B**: MCP tool discovery relies on structured JSON schemas; explicitly defining required parameters and data types ensures the harness validates inputs before invoking the tool. (W02.L2.C3)
- Quiz 4: **C**: Lazy tool registration avoids context pollution by presenting only relevant context or high-level summaries initially, providing full tool schemas on demand to keep token overhead low and improve tool selection accuracy. (W02.L2.C4)
