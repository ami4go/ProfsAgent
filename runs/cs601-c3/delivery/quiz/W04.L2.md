# Review quiz · W04.L2 · Standards and specification guidelines for use cases

## Recap of the previous lecture (5 min)

1. A developer builds an MCP server function that receives payloads from an LLM call. The static analyzer throws a warning regarding untyped JSON schema bindings. Why is this flagged as a risk for production tool integration?
   - A. Untyped bindings prevent the agent workspace from opening network connections.
   - B. Untyped bindings allow unexpected payload structures from the LLM to cause unhandled runtime errors.
   - C. The linter requires all JSON schema payloads to be encrypted prior to parsing.
   - D. Static analyzers cannot parse async functions unless parameters are strings.

2. In an agent workspace pipeline, all functional integration tests for an MCP tool pass, yet the build fails static validation. What is the most likely cause based on production standards?
   - A. The test harness requires manual user confirmation for each tool execution.
   - B. The server implementation contains unresolved static analysis warnings.
   - C. The agent workspace environment only supports synchronous tool integration.
   - D. Integration tests cannot run alongside linter checks.

## Review quiz (10 min)

1. Why does relying on unstructured product descriptions frequently lead to scope creep in software development?
   - A. Unstructured descriptions lack defined system boundaries, allowing implicit assumptions to expand project scope.
   - B. Unstructured descriptions restrict system actors to a single administrative role.
   - C. Unstructured descriptions strictly enforce ISO standards, which slows down core feature development.
   - D. Developers cannot convert text to code without automated translation tools.

2. In a food delivery app, a customer places an order, and the app uses a third-party payment gateway to authorize credit cards. How is the payment gateway classified?
   - A. System Boundary
   - B. Secondary Supporting Actor
   - C. Primary Actor
   - D. Internal Automated Process

3. How does Cockburn's casual/brief use case format differ from a fully dressed use case format?
   - A. Brief formats specify database schema tables, while fully dressed formats describe UI mockups.
   - B. Brief formats summarize the main scenario in a brief paragraph, whereas fully dressed formats detail preconditions, guarantees, and extension flows.
   - C. Brief formats document third-party systems, while fully dressed formats document internal users.
   - D. Brief formats are written in passive voice, whereas fully dressed formats require active voice.

4. A raw narrative states: 'When the buyer clicks the green button on the React dashboard, the server saves the product to the wishlist table.' Applying extraction heuristics, which clean actor-goal pair should be created?
   - A. Buyer -> Add product to wishlist
   - B. Server -> Render wishlist screen
   - C. Buyer -> Click green button
   - D. React Dashboard -> Save product to table

5. Which of the following steps follows standard guidelines for writing steps in a Main Success Scenario?
   - A. The Customer enters shipping address and submits the order.
   - B. System should show a pop-up confirmation screen to user.
   - C. The credit card details are validated by the system.
   - D. Password verification occurs on the server background worker.

6. A product prompt reads: 'The user creates an account, searches for items, adds them to cart, and pays using UPI.' When structuring this prompt into formal use case outlines, what is the best approach?
   - A. Split the compound goals into separate use cases like 'Search Items' and 'Checkout Order'.
   - B. Define the entire prompt as a system boundary instead of a set of use cases.
   - C. Exclude the payment phase because third-party integrations cannot be documented.
   - D. Merge all tasks into a single 20-step use case called 'User Operations'.

7. What is the primary purpose of specifying a 'Precondition' in a standard use case document?
   - A. To detail the user interface layout required for the initial screen.
   - B. To list all secondary external systems involved in the main scenario.
   - C. To define the final outcome guaranteed by the system after an error occurs.
   - D. To describe what must be true about the state of the system before the use case can start.

8. A reviewer examines a use case step stating: 'The system opens a red pop-up modal dialog to alert the user of insufficient funds.' What quality defect is present, and how should it be resolved?

## Answers

- Recap 1: **B**: Untyped JSON bindings allow malformed or unexpected responses from the LLM to bypass type checks, potentially causing runtime crashes in the tool handler. (W04.L1.C1)
- Recap 2: **B**: Production-grade tool configuration requires both all functional tests to pass and zero static analysis warnings from configured linters. (W04.L1.C2)
- Quiz 1: **A**: Without standardized specifications and clear system boundaries, informal descriptions leave room for ambiguity and unvetted features, causing scope creep. (W04.L2.C1)
- Quiz 2: **B**: External services or systems that interact with the system to help fulfill a primary actor's goal are classified as secondary supporting actors. (W04.L2.C2)
- Quiz 3: **B**: Brief use cases offer a quick paragraph summary of successful goal completion, while fully dressed use cases comprehensively detail preconditions, failure branches, and guarantees. (W04.L2.C3)
- Quiz 4: **A**: Extraction heuristics filter out UI elements (green button, React dashboard) and technical implementation details (wishlist table) to capture the core domain goal: 'Add product to wishlist'. (W04.L2.C4)
- Quiz 5: **A**: Standard guidelines require steps to be written in active voice with an explicit Subject-Verb-Object structure (e.g., 'The Customer enters...'). (W04.L2.C5)
- Quiz 6: **A**: Messy feature narratives containing multiple independent goals should be split into distinct, focused use cases to clarify boundaries and maintain spec readability. (W04.L2.C6)
- Quiz 7: **D**: Preconditions state the required system state or environmental conditions that must be satisfied before the use case begins execution. (W04.L2.C7)
- Quiz 8: **This step exhibits a boundary leak by specifying concrete UI implementation details (red pop-up modal). It should be rewritten to focus on functional intent, such as 'The system notifies the user of insufficient funds.'**: Use case quality checklists penalize UI design leaks (colors, pop-up modals) because specifications should remain technology-agnostic and testable at the functional level. (W04.L2.C8)
