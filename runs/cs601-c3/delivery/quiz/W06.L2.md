# Review quiz · W06.L2 · Requirements to executable specifications and code generation

## Recap of the previous lecture (5 min)

1. You need to convert an informal requirement—'Calculate discount based on user age and loyalty points, failing gracefully on invalid inputs'—into an unambiguous contract for an AI code generator. Which interface specification best achieves this?
   - A. def calculate_discount(age: int, points: int) -> float (raises ValueError for negative inputs)
   - B. def calculate_discount(age: str, points: str) -> int
   - C. def calculate_discount(age, points)
   - D. def calculate_discount(user_info: dict) -> any

2. In a Design by Contract specification for a BankAccount class, a developer asserts that `balance >= 0` must evaluate to true before and after any public method execution. What type of contract constraint is this?
   - A. Class Invariant
   - B. Precondition
   - C. Postcondition
   - D. Input Boundary Condition

3. An automated testing tool reads an executable contract and generates hundreds of randomized integer inputs to verify that a sorting method always returns a sorted list. Which technique is the framework demonstrating?
   - A. Static Code Linting
   - B. Mock Server Simulation
   - C. Property-Based Test Generation
   - D. Manual Unit Testing

## Review quiz (10 min)

1. A requirement states: 'A user cannot withdraw an amount exceeding their current balance.' In contract-based design, how is this constraint formally classified for the withdraw method?
   - A. As an implicit parameter signature definition
   - B. As a postcondition that guarantees the balance becomes zero after execution
   - C. As a precondition that must be satisfied by the caller before invoking withdraw
   - D. As a class invariant that applies only when the system shuts down

2. You are defining a pytest-bdd scenario for an e-commerce checkout module. Which action correctly belongs in the step implementation of a 'Given' clause?
   - A. Asserting that the database record status equals COMPLETED
   - B. Initializing a user account with an active balance and populating their shopping cart
   - C. Handling an exception thrown during payment processing
   - D. Calling the checkout() API method on the cart object

3. A payment system requirement specifies that attempting to charge an expired credit card must raise an ExpiredCardException. How should an assertion harness systematically verify this requirement?
   - A. By asserting that the method returns a null transaction ID
   - B. By updating the card expiration date inside the postcondition assertion block
   - C. By verifying that the account balance remains unchanged after calling a non-existent method
   - D. By executing the API call within an assertion harness configured to expect ExpiredCardException

4. An LLM tasked with generating executable BDD step definitions frequently invents non-existent method signatures. Which prompting strategy directly mitigates these interface hallucinations?
   - A. Instructing the LLM to omit assertions from the generated test code
   - B. Asking the LLM to generate plain natural-language summaries before code generation
   - C. Removing key preconditions and postconditions from the prompt text
   - D. Anchoring the system prompt with explicit interface schemas and method signatures

5. Before the core logic of a SessionManager class is written, how can you confirm that your newly authored BDD executable specification suite correctly targets the public interface?
   - A. Replace all Given-When-Then assertions with hardcoded passing booleans
   - B. Execute the spec suite against stub interfaces to confirm method binding and assertion failures
   - C. Disable step definition hooks until full implementation is deployed
   - D. Perform a static text code review without executing the spec framework

## Answers

- Recap 1: **A**: Specifying precise type annotations (`int -> float`) and explicit exception behavior (`raises ValueError`) eliminates ambiguity in method signatures, preventing runtime errors during AI code generation. (W06.L1.C1)
- Recap 2: **A**: A condition that must always remain true before and after the execution of every public method in a module is a class invariant. (W06.L1.C2)
- Recap 3: **C**: Executable specifications allow frameworks to automatically synthesize property-based tests that validate general rules across wide ranges of generated inputs. (W06.L1.C3)
- Quiz 1: **C**: Preconditions specify the criteria and obligations that must be true prior to invoking a method, such as validating that the requested withdrawal amount does not exceed the balance. (W06.L2.C1)
- Quiz 2: **B**: In spec-driven BDD frameworks, 'Given' steps set up the required initial context and state before any action or triggering event occurs. (W06.L2.C2)
- Quiz 3: **D**: Translating exception requirements into executable specifications requires wrapping the target method call in an assertion harness that validates the expected exception is raised. (W06.L2.C3)
- Quiz 4: **D**: Schema anchoring provides explicit method signatures and parameter contracts in the prompt, constraining the LLM to generate specs using real, verified interfaces. (W06.L2.C4)
- Quiz 5: **B**: Running specifications against stub interfaces verifies that step definitions bind correctly to method signatures and fail appropriately before full development. (W06.L2.C5)
