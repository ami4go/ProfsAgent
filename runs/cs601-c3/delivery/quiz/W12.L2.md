# Review quiz · W12.L2 · Deployment and reliability metric evaluation

## Recap of the previous lecture (5 min)

1. Why is it necessary to map automated testing pipeline stages back to explicit reliability requirements before evaluating a pipeline?
   - A. It eliminates the need for manual code reviews in multi-component software factories.
   - B. It replaces the need for defining Service-Level Objectives across AI services.
   - C. It ensures every test stage directly validates at least one target reliability objective rather than testing arbitrarily.
   - D. It automatically guarantees zero downstream production failures regardless of test quality.

2. An AI-native application relies on three cascading microservices. If upstream Service A fails, it triggers downstream failures in Services B and C. Which mechanism should be incorporated into the reliability specification to mitigate this?
   - A. Increase the error budget of Service C to absorb model drift.
   - B. Increase the test coverage threshold of Service B's unit tests to 100%.
   - C. Replace all automated integration tests with manual end-to-end checks.
   - D. Define a cascade failure policy such as circuit breaking or fallback responses between services.

3. An engineering team instrumented their production AI pipeline with real-time dynamic data profiling, but observed a significant increase in pipeline execution cost and latency. What trade-off is demonstrated in this case study?
   - A. Deterministic output generation vs. stochastic model training speed.
   - B. High test coverage vs. zero security vulnerability detection.
   - C. Deep operational observability vs. resource consumption and execution latency.
   - D. Automated integration testing vs. manual test writing effort.

## Review quiz (10 min)

1. How does measuring rollback time specifically help evaluate the health of a deployment pipeline?
   - A. It indicates how quickly the system can revert to a stable state when a deployment introduces critical bugs.
   - B. It directly tracks the rate of total requests processed per second during normal operation.
   - C. It determines how frequently developers are committing code to the production branch.
   - D. It measures the maximum network bandwidth available during high-traffic deployments.

2. If a service consumes its entire error budget midway through a release cycle, how should this affect future release decisions?
   - A. The service level objective (SLO) should be permanently lowered to allow more failures.
   - B. The team should ignore error budgets and rely only on availability metrics for releases.
   - C. New feature releases should be paused to focus on system stability and bug fixes.
   - D. Deployment frequency must be immediately increased to clear the remaining budget.

3. A developer is tracing a request passing through three microservices using OpenTelemetry SDKs. The traces appear as three disconnected spans instead of one unified trace. Which configuration is missing?
   - A. Context propagation across HTTP or gRPC boundaries between services.
   - B. Custom logging configuration for stdout printing.
   - C. Error budget tracking rules in the OpenTelemetry SDK.
   - D. Prometheus metric exporter configuration in the API gateway.

4. An engineering team wants Grafana to warn them before a minor issue completely exhausts their reliability budget. Which alerting configuration is best suited for this?
   - A. Daily automated email reports summarizing total HTTP status codes.
   - B. Standard alerts on overall CPU utilization exceeding 95%.
   - C. Alert rules set on the error-budget burn rate.
   - D. Alerts triggered only when MTBF reaches zero.

5. During a load test executed with k6, an engineer uses Chaos Mesh to inject latency into the database. The latency SLI breaches the defined SLO, but the error rate remains low. What does this reveal about the system?
   - A. The system is operating within all defined reliability targets and requires no adjustment.
   - B. The service processes requests without dropping them, but fails to satisfy response-time targets under failure conditions.
   - C. Chaos Mesh failed to inject failure because the overall error rate did not increase.
   - D. The k6 load generator automatically mitigated the failure by throttling request throughput.

6. Before deploying a new release, a team observes that the update increases throughput by 20% but causes the error-budget burn rate to exceed acceptable limits. What is the most appropriate release decision?
   - A. Recommend a Go decision because throughput improvements outweigh reliability risks.
   - B. Proceed with the release but disable telemetry exporters to suppress alerts.
   - C. Recommend a No-Go decision until the high burn rate issue is resolved.
   - D. Increase the SLO target immediately to render the current burn rate acceptable.

## Answers

- Recap 1: **C**: Mapping pipeline stages to explicit reliability requirements ensures that test design decisions directly serve specific system reliability objectives rather than performing redundant or unaligned testing. (W12.L1.C1)
- Recap 2: **D**: Formalizing a cascade failure policy (e.g., using circuit breakers or fallbacks) prevents an upstream failure in a multi-component AI system from causing dependent downstream services to fail. (W12.L1.C2)
- Recap 3: **C**: Instrumenting deep observability in production pipelines often improves visibility into reliability failures, but comes at the expense of higher resource utilization and execution delays. (W12.L1.C3)
- Quiz 1: **A**: Rollback time measures the speed at which a deployment pipeline can revert to a known stable version when a release causes failures. (W12.L2.C1)
- Quiz 2: **C**: Error budgets guide release decisions, so exhausting the budget signals that feature deployments should halt until system stability is restored. (W12.L2.C2)
- Quiz 3: **A**: Context propagation carries trace IDs across network boundaries so OpenTelemetry can join individual service spans into a single trace. (W12.L2.C3)
- Quiz 4: **C**: Monitoring and setting alert rules on the error-budget burn rate flags rapid budget consumption early before the error budget is entirely depleted. (W12.L2.C4)
- Quiz 5: **B**: Breaching the latency SLO while keeping error rates low indicates that requests succeed but take unacceptably long to complete under injected failure. (W12.L2.C5)
- Quiz 6: **C**: Release decisions prioritize defined SLOs and error budget health; a high burn rate introduces unacceptable risk to reliability despite throughput gains. (W12.L2.C6)
