## 2 · Course context (paste as a text source)

```text
COURSE: Software Development using AI (IIIT-Delhi, level 3xx, 3/4-year B.Tech students)
LECTURE: W12.L1 · week 12 · Reliable and safe trustworthy software architectures (90 minutes)

LEARNING OUTCOMES (what students must be able to do):
- Assess automated testing pipelines for AI-native software factories, for a supplied multi-component software project, justifying each design decision against at least one stated reliability requirement.

STUDENTS ALREADY KNOW:
- Automated testing and evaluation mechanisms (week 10)
- AI-native factory pipeline architecture overview (earlier lecture on this topic)
- Automated testing stages in AI pipelines (earlier lecture on this topic)
- Mapping reliability requirements to pipeline stages (earlier lecture on this topic)
- Worked example: assessing sample pipeline reliability (earlier lecture on this topic)

THIS LECTURE, PART BY PART:
1. Recap: pipeline assessment criteria discussion (10 min, discussion)
   Teaches: Students will briefly revisit the assessment criteria and reliability requirement mappings covered previously, clarifying any gaps through instructor-led discussion. This sets the context for deeper analysis of a multi-component project.
   Key terms: recap, assessment criteria, reliability requirements, discussion
2. Defining reliability requirements for multi-component AI (15 min, mechanism)
   Teaches: Students will learn how to elicit and formalize reliability requirements for a system composed of multiple AI services (e.g., service-level objectives, error budgets, cascade failure policies). They will apply a template to a supplied project description.
   Key terms: service-level objectives, error budgets, cascade failure, requirements elicitation, multi-component
3. Case study: industry AI pipeline reliability (15 min, case study)
   Teaches: Students will examine a real-world case study of an AI-native pipeline in production, focusing on how the organization defined reliability requirements, instrumented testing stages, and measured outcomes. They will analyse trade-offs made by the team.
   Key terms: case study, production pipeline, instrumentation, trade-offs, outcomes
4. Worked example: assessing supplied project pipeline (20 min, worked example)
   Teaches: The instructor demonstrates a full assessment of the supplied multi-component software project's testing pipeline, linking each design decision to a specific reliability requirement and showing how to document justifications. Students follow the reasoning step by step.
   Key terms: worked example, supplied project, design decisions, justification, documentation
5. Group activity: assess pipeline and justify (20 min, activity)
   Teaches: In small groups, students receive a different pipeline configuration for the same project and must assess it against the reliability requirements, producing a written justification for each design decision. Groups present findings for peer review.
   Key terms: group activity, assessment, justification, peer review, pipeline configuration
6. Trade-offs: testing depth vs deployment speed (10 min, comparison)
   Teaches: Students will compare the impact of increasing test coverage and rigor on deployment latency and resource consumption. They will evaluate scenarios where faster deployment may be preferred over exhaustive testing, supporting arguments with metrics.
   Key terms: trade-offs, test coverage, deployment latency, resource consumption, metrics

COMES LATER (do not teach here):
- Deployment and reliability metric evaluation (week 12)
```
